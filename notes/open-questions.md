## 使用言語の選定

レイアウトエンジン、API サーバー（design.md §1.1）、クライアント（SPA）を書く言語を、次の 3 つの構成から選ぶ。どの構成でもクライアントは TypeScript で書く。

- 構成 A: すべて TypeScript で書く
- 構成 B: サーバーとレイアウトエンジンを Rust で書く。SPA 向けにはレイアウトエンジンを WASM にする
- 構成 C: 構成 A のうち、レイアウトエンジンのコアだけを MoonBit（JS バックエンド）で書く

### 言語選定の動機

リライト元は TypeScript で書かれており、命令的なコードに流れやすく、型定義が分散していた。リライトでは関数型スタイルに寄せる。

レンダラーをアプリに組み込んで mermaid のように使うため、レイアウトエンジンは JS か WASM にコンパイルできる言語で書く必要がある。

リライト元のサーバー（`apps/server/api/src`、テストを除いて約 23,000 行）の中身は、データソースのポーリング、同期ジョブとその計画、観測データの統合、メトリクス、認証、スケジューラーである。状態の遷移、失敗の扱い、並行処理、I/O が絡み、ADT、`Result`、網羅的なパターンマッチといった言語の表現力が効く。言語の表現力は、レイアウトエンジンよりサーバーで効く。

### リポジトリ内の言語の数

リポジトリ内の言語は 2 つまでにする。サーバーとレイアウトエンジンを、TypeScript 以外の別々の言語で書くと、クライアントの TypeScript と合わせて 3 つになる。この理由で、Rust のサーバーと MoonBit のレイアウトエンジンの組み合わせや、Scala か Elixir のサーバー（「サーバーの言語候補から外したもの」）を外した。

プラグインはスクリプト言語で書いて WASM で動かす（「プラグインの言語の選定」）ので、この数には含めない。

### 構成 A: すべて TypeScript

レイアウトエンジンは、lint（`let`、引数の再代入、破壊的な配列メソッドの禁止）と型を 1 モジュールに集める構成で関数型スタイルを守る。パターンマッチやイミュータブルなデータは言語の機能ではないので、ts-pattern などのランタイムに残るライブラリを入れるか、`switch` と `readonly` で冗長に書くかのどちらかになる。

サーバーは Effect で関数型スタイルに寄せる。サーバーなので、ランタイムに残るライブラリのサイズは問題にならない。

利点:

- モデル、観測データの統合、レイアウトエンジンを、サーバーと SPA で 1 つの実装として共有できる
- WASM のプラグインを Node.js がそのまま実行できる
- Effect に、型付きのエラー、依存の注入、並行処理、リトライとスケジューリングがあり、ポーリングや同期ジョブに合う

欠点:

- Effect の学習コストが高い
- 関数型スタイルを言語ではなくライブラリで得るので、ADT やパターンマッチは Rust や MoonBit より冗長になる
- Rust よりメモリの消費が大きい

### 構成 B: サーバーとレイアウトエンジンを Rust

利点:

- サーバーのロジックで効く表現力（ADT、`Result`、網羅的なパターンマッチ）が言語に組み込まれている
- WASM のホストとして強い。wasmtime は Rust のネイティブのライブラリで、Component Model でプラグインのインターフェースを型付きで定義できる
- 単一のバイナリで配れ、メモリの消費が小さい
- サーバーはレイアウトエンジンのクレートをネイティブのライブラリとしてリンクできる。WASM も JSON も要らず、型をサーバーとレイアウトエンジンで共有できる
- SPA 向けには同じクレートを WASM にし、`tsify` と `serde-wasm-bindgen` で `.d.ts` を生成する。serde のタグ付きの `enum` は判別可能な union になる

欠点:

- 非同期 Rust が複雑
- コンパイルに時間がかかる
- 学習コストが TypeScript より高い
- 観測データの統合をブラウザのエディタでも使うなら、Rust と TypeScript の二重実装になる

レイアウトエンジンを Rust で書くときの問題は、次のように対処する。

- 所有権モデルのためにグラフを扱うコードが書きにくい問題は、ノードやポートを `NodeId(u32)` のような ID で参照し、レイアウトの各段を新しい出力を返す関数にすれば軽くなる。構造を共有したいときは、型にライフタイムが出る `Cow<'a, T>` より、`Rc::make_mut` / `Arc::make_mut` か永続データ構造の `im` クレートを使う
- ブラウザでは WASM になるので非同期の初期化が要る。ただし mermaid の `render()` も非同期なので、組み込む側の使い勝手は変わらない
- バンドラーの設定は、WASM を JS に埋め込めば要らない。その代わりサイズが 3 割ほど増える
- エディタでドラッグ中にフレームごとに呼ぶと、serde の変換のコストがかかる。状態を WASM 側に持たせてハンドルで操作するか、軽い処理を TypeScript 側に置く

### 構成 C: レイアウトエンジンのコアだけを MoonBit

構成 A のうち、レイアウトエンジンのコアだけを MoonBit で書き、JS バックエンドで出力する。サーバーは TypeScript なので、Node.js が JS をそのまま実行する。

利点:

- ADT、パターンマッチ、イミュータブルな既定値がある。GC があるので、所有権モデルのためにグラフを扱うコードが書きにくくなることがない
- パターンマッチやイミュータブルなデータは言語の機能なので、ランタイムにライブラリが残らない
- JS バックエンドがあるので、WASM で問題になる非同期の初期化、バンドラーの設定、SSR や Edge ランタイムでの読み込みを避けられる
- レイアウトの計算は外部への依存が少ないので、エコシステムが薄くても困りにくい
- 「レイアウトエンジンの境界」を守れば、MoonBit をやめてもコアを TypeScript で書き直すだけで構成 A に戻れる

欠点:

- 言語の表現力が効くのはレイアウトエンジンだけで、サーバーには効かない
- 言語がまだ 1.0 に達していない（0.8 系の時点で検討した）。ベータでコア言語は安定したと宣言されているが、標準ライブラリとツールチェーンは固まっていない。1.0 が出たら見直す
- グラフ、幾何、テストまわりのライブラリは自作になる可能性が高い
- 書ける人が少ない。コーディングエージェントも TypeScript ほど正確に書けない可能性がある
- TypeScript との境界の型は MoonBit 側を正本にし、MoonBit が公式に生成する `.d.ts` を使う。生成される型には `any` が混ざることがあり、精度が足りなければ薄い `.d.ts` を手で書く。mizchi/mbts（`.mbti` と `.d.ts` の相互変換）は開発が止まっているので依存しない。MoonBit の `struct` と `enum` が JS 上でどう表現されるかは未確認で、TypeScript 側で値を直接組み立てられない場合は、MoonBit 側から生成用の関数を公開するか、JSON を経由する

### レイアウトエンジンの境界

どの構成でも、レイアウトエンジンのコアを「データを受け取り、データを返す」純粋関数にし、境界は入力と出力の 2 つの型だけにする。構成 B と C では、この境界が言語の境界になる。

```
TS: パース → テキスト計測 → [サイズ付きグラフ]
                                ↓
コア: 配置・ルーティング・探索（純粋関数）
                                ↓
TS: [座標付きレイアウト] → レンダラー / エディタ
```

リライト元のレイアウト処理からコアの外に出す必要があるものは次のとおり。

- テキスト計測（`engine/text-measurer.ts`）。DOM に触れているのはここだけだった。コールバックで注入せず、TypeScript 側で先に測ってサイズ付きのグラフを渡す。こうすると FFI が要らない
- 探索の `await` と時間予算（`composite/search.ts` の `budgeted(...)`）。時計に依存するので純粋なコアに入れられない。予算を試行回数で数えるか、探索を 1 ステップずつ返してループと打ち切りを TypeScript 側に持たせる
- エディタとのつなぎ込み（`interaction.ts`）は TypeScript 側に残す

SVG の組み立てはレンダラーが TypeScript のテンプレートで行う。レイアウトは幾何データだけを返し、パスも `d` 文字列ではなくセグメント列で返す。

### レイアウトエンジンの性能

- リライト元で Worker を使うのはサーバーの `apps/server/api/src/services/derivation.ts` だけで、目的はイベントループを止めないことだった。トポロジー 1 件につき Worker を 1 つ立て、その中でレイアウトをシングルスレッドで計算している。どの構成でも同じ構成を取れる
- 並列化するときは、複数の Worker を立て、それぞれでコアを呼ぶ。探索を 1 ステップずつ返す形にしておけば、`composite/search.ts` の候補を並列に評価できる
- ブラウザで共有メモリのスレッドを使うには `SharedArrayBuffer` と COOP/COEP ヘッダーが要る。他人のページに組み込むライブラリでは現実的でないので、構成 B でも Worker で分ける

言語による高速化には期待しない。MoonBit の JS バックエンドなら手書きの JS とほぼ同じ速度になると見込む。WASM で速くなっても、境界のデータ変換で相殺されうる。リライト元で大きなレイアウトに数分かかっていた原因は探索の計算量だと考えている（未計測）。そうであれば、言語を変えても解決しない。

### 構成の選択と連動して決まること

- レイアウトをどこで計算するか。リライト元では大きなトポロジーのレイアウトに数分かかり、サーバーで事前に計算して保存していた。ブラウザで毎回計算する、ブラウザで計算して API で保存する、サーバーで計算する、のどれにするか
- サーバー側でのエクスポートが要るか。PNG や SVG を画像の URL として他のページに埋め込むなら、サーバーでレンダリングする必要がある。構成 B ではレンダラーが Rust と TypeScript の二重になる
- 観測データの統合をどこに置くか。ブラウザのエディタでも使うなら、構成 B では二重実装になる

### 試作で確かめること

リライト元のレイアウト処理から代表的な一部（`role-tiers` か `route-edges`）を Rust と MoonBit に移植し、TypeScript で書いた同じ処理と比べる。

1. 出力サイズと、TypeScript から呼んだときの API の使い心地（構成 B は WASM、構成 C は JS）
2. 境界の型。構成 B は `tsify` が生成する `.d.ts` の精度。構成 C は公式の `.d.ts` の精度、MoonBit の値の JS 上の表現（`enum` の `$tag` など）が仕様として安定しているか、TypeScript 側で境界の値を直接組み立てられるか
3. 純粋なコアとして切り出せるか（テキスト計測と時間予算を外に出せるか）
4. TypeScript 版との性能比較。構成 C では JS と WASM のどちらのバックエンドを使うかを決める材料にする
5. エディタのドラッグ中に呼ぶときのコスト
6. MoonBit の直近のリリースでの破壊的変更の頻度と、追従にかかるコスト
7. コーディングエージェントに書かせたときのコードの品質
8. TypeScript 版と比べて、読みやすさと書きやすさに明確な差があるか

### 構成の判断基準

- 構成 C は、「試作で確かめること」の 1〜3 に問題がなく、6 が許容範囲で、8 で明確な差があれば採る
- 構成 B は、試作の結果に加えて、サーバーのロジックを Rust で書く利点が、Rust の欠点に見合うかで決める
- どちらも採らなければ構成 A にする

### レイアウトエンジンの言語候補から外したもの

JS か WASM にコンパイルできる言語を候補にし、TypeScript、Rust、MoonBit 以外は次の理由で外した。

- Elm は、JS から関数として呼べないので外した。JS とのやり取りは非同期の ports に限られ、同期の `layout(graph)` を提供できない。0.19.1 からリリースも止まっている
- PureScript はエコシステムと成熟度で外した
- Scala.js は、TypeScript との境界の型を扱いにくいので外した。Scala 3 で `.d.ts` を生成する道具がなく（sbt-scala-ts は Scala 2 系だけに対応する）、型を TypeScript 側で定義して ScalablyTyped で取り込むしかない。Scala 3 の高い表現力（型クラス、高カインド型など）も、純粋な計算のコアでは要らない
- Gleam は型の表現力が低く、制約を強めた TypeScript と大差ない。エコシステムもないので外した
- ReScript は、前身の BuckleScript の作者が MoonBit を率いており、今後伸びるのは MoonBit の方だと見込んで外した。ReScript は別のコアチームが開発を続けている。境界の型（`genType` による `.d.ts` の生成）と安定性が確かめられている点は MoonBit より有利だった
- OCaml（Melange / wasm_of_ocaml）は、ツールチェーン（dune、opam、Melange、JS のバンドラー）が重いので外した
- F#（Fable）は、.NET の標準ライブラリに依存したコードが JS に変換できないことがあり、Scala.js と同じく元のプラットフォームから引き継ぐ問題があるので外した
- Haskell は、GHC の JS バックエンドと WASM バックエンドが未成熟で、出力も重いので外した
- Kotlin/JS は、関数型が主体の言語ではなく、出力も重いので外した
- Roc、Koka、Grain は、研究段階かプレリリースで MoonBit より未成熟なので外した
- Go は WASM の出力サイズが大きいので外した

### サーバーの言語候補から外したもの

Scala と Elixir は、サーバーの言語としては悪くないが、リポジトリ内の言語が 3 つになるので外した（「リポジトリ内の言語の数」）。どちらもレイアウトエンジンを書けないため、レイアウトエンジンを書く言語が別に要る。

- Scala 3（JVM）: 型付きの副作用を扱うライブラリ（ZIO、Cats Effect）が最も成熟しており、型クラスや高カインド型といった表現力がサーバーのロジックで効く。WASM のプラグインは Chicory（Bytecode Alliance に移って Endive になった。QuickJS を動かす実績がある）で動かせる。長く動き続けるプロセスなので、JVM の起動時間やメモリの消費は大きな差にならない
- Elixir: BEAM はプロセスごとにヒープが分かれ、プリエンプティブにスケジュールされるので、プラグインだけでなくホスト自身のコードにバグがあっても、そのプロセスだけが落ちて全体は止まらない。スーパーバイザーが落ちたプロセスを再起動する。WASM は Wasmex（wasmtime を Rust の NIF として組み込んだライブラリ。Component Model に対応）で動かせる。ただし NIF の中でネイティブのコードがクラッシュすると BEAM 全体が落ちる。イミュータブルが基本なので、型が弱くても共有された状態が壊れる種類のバグは起きにくい。型システムは、v1.20 で型推論による段階的な検査が入ったが、利用者が型を定義する手段はまだない（型付きの構造体は v1.21、型シグネチャは v1.22 で予定されている）

ほかに次の言語を外した。

- F#（.NET）は、構文のなじみやすさとエコシステムで Scala に劣るので外した。WASM のホストは公式の wasmtime-dotnet があり、Scala より素直である
- Kotlin（JVM）は、関数型が主体の言語ではないので外した。関数型に寄せるなら Scala を選ぶ
- Haskell は、ツールチェーンが重く、書ける人が少ないので外した
- OCaml は、ツールチェーンが重いので外した。wasmtime のバインディングも 0.0.3（wasmtime v0.22 に対応）で止まっており、WASM のホストとして弱い
- Gleam は、型の表現力が低いので外した。BEAM の並行処理はポーリングに向いている
- Go は、ADT がなく、関数型スタイルに寄せる動機に合わないので外した
- MoonBit（ネイティブ）は、サーバー向けのエコシステム（HTTP、DB、認証）がほとんどないので外した

プラグインが落ちても全体が止まらない隔離は、どの言語でも WASM のサンドボックスで得られる。wasmtime では、プラグインの trap はホストにエラー値として返り、メモリと実行時間に上限をかけられる。落ちた後の再起動は、Rust なら tokio のタスクの監視かアクターのライブラリ（ractor など）で書く。

## プラグインの言語の選定

データソースのプラグインを書く言語を選ぶ。プラグインは WASM で動かし、スクリプト言語はインタプリタを WASM にしたものを同梱する構成にする。同梱するスクリプト言語は JavaScript（QuickJS）を第一候補にしている。

### プラグインの言語への要件

- ネットワークエンジニアがコーディングエージェントに書かせて、すぐに試せる。コンパイルの手順を挟まないスクリプト言語で書ける
- サンドボックスで動かす。HTTP などの I/O は、ホストが許可リスト付きの関数として渡す

リライト元では、プラグインを TypeScript で書き、QuickJS の WASI ビルド（`quickjs-wasi`）で動かしている（`apps/server/api/src/plugins/sandbox/quickjs-vm.ts`）。データソースごとに VM を分け、メモリの上限、割り込みの期限、ネットワークのポリシー付きの `fetch` を実装している。Zabbix、NetBox、Prometheus、Grafana など 9 つのプラグインがある。

### WASM を土台にするプラグインの構成

- ホストとプラグインのインターフェースは WASM のモジュールとして定義する。ホストは WASM だけを知っていればよい。Component Model の WIT で定義するかは未決
- スクリプト言語は、Shumoku がインタプリタを WASM にビルドして同梱する。利用者はスクリプトを書くだけで、コンパイルは要らない
- Rust、Go（TinyGo）、MoonBit などで書いて WASM にコンパイルしたプラグインも、同じインターフェースに合わせれば動く
- サンドボックスは WASM のランタイムに一本化する
- WASI のモジュールなので、同じ `.wasm` を Rust のサーバーなら wasmtime で、TypeScript のサーバーなら Node.js で動かせる。サーバーの言語とは独立に決められる
- インタプリタを WASM の中で動かす分だけ遅くなるが、プラグインの処理はデータソースへの HTTP の待ち時間が中心なので問題になりにくい

### 同梱するスクリプト言語の候補

- JavaScript（QuickJS）: 第一候補。次の理由による
  - QuickJS を WASM で動かす実績が多い。Shopify の Javy（Shopify Functions で本番運用されている）や Extism の JS PDK が QuickJS を使っている
  - リライト元の `quickjs-vm.ts` の設計（VM の分離、メモリの上限、割り込みの期限、ポリシー付きの `fetch`）を引き継げる
  - コーディングエージェントが正確に書ける。リライト元の 9 つのプラグインを移植の出発点にできる
  - QuickJS は WASM の中で同期的に動くので、非同期の I/O はホストが作り込む。ホストの `fetch` が完了したらホストがゲストに入り直し、溜まった Promise のジョブを実行する。リライト元はこの形を実装済み
  - 型チェックはない。TypeScript で書けるようにするなら、どこかで型を取り除く
- Luau: Roblox が開発している Lua の派生言語。段階的な型付けで、コンパイルの手順なしに型チェックが効く。最大の利点である言語に組み込まれたサンドボックスは、WASM の中で動かすとランタイムのサンドボックスと二重になり、利点が薄れる。WASM の中でホストから I/O を受け取るプラグインとして動かした事例がほとんど見当たらない。ネットワークエンジニアにはなじみが薄い
- Starlark: Python の方言で、Bazel のビルド設定などに使われている。ネットワークエンジニアになじみのある Python に構文が近い。I/O を持たない同期の言語で、クラスと例外がない。Rust 実装の `starlark-rust` はあるが、WASM の中で動かす事例は確かめていない

| 観点 | JavaScript | Luau | Starlark |
|---|---|---|---|
| ネットワークエンジニアのなじみ | 中くらい | 低い | 高い（Python に近い） |
| コーディングエージェントの精度 | 高い | 中くらい | 中〜高（Python との違いで誤りやすい） |
| WASM で動かす実績 | 多い | 少ない | 確かめていない |
| コンパイルなしの型チェック | ない | ある | 一部ある |
| 非同期の I/O | Promise | コルーチン | ない（ホストに任せる） |
| リライト元のプラグイン | 移植しやすい | 書き直し | 書き直し |

### プラグインの言語の決め方

JavaScript（QuickJS）について次を確かめ、問題がなければ採る。

1. データソースのプラグインを 1 つ（たとえば Zabbix）コーディングエージェントに JavaScript で書かせ、書かれたコードがそのまま動くか
2. TypeScript で書けるようにする場合、型を取り除く処理をどこで行うか（ホストが読み込むとき、利用者の手元のツール、など）
