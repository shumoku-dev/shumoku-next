## 使用言語の選定

レイアウトエンジンのコアだけを MoonBit で書き、それ以外（パース、テキスト計測、レンダラー、エディタ、CLI、サーバー）は TypeScript で書く案を検討している。試作で判断する。

### 動機

リライト元は TypeScript で書かれており、命令的なコードに流れやすく、型定義が分散していた。リライトでは関数型スタイルに寄せる。

レンダラーをアプリに組み込んで mermaid のように使うため、レイアウトエンジンは JS か WASM にコンパイルできる言語で書く必要がある。

### 言語候補の絞り込み

JS か WASM にコンパイルできる言語を候補にし、TypeScript と MoonBit 以外は次の理由で外した。

- Elm と PureScript はエコシステムと成熟度で外した
- Scala.js はバンドルサイズが大きいことと、JVM のライブラリに依存したコードを JS で動かせないことで外した
- Gleam は型の表現力が低く、制約を強めた TypeScript と大差ない。エコシステムもないので外した
- ReScript は、前身の BuckleScript の作者が MoonBit を率いており、今後伸びるのは MoonBit の方だと見込んで外した。ReScript は別のコアチームが開発を続けている。境界の型（`genType` による `.d.ts` の生成）と安定性が確かめられている点は MoonBit より有利だった
- OCaml（Melange / wasm_of_ocaml）は、ツールチェーン（dune、opam、Melange、JS のバンドラー）が重く、日本語の情報が少ないので外した
- F#（Fable）は、.NET の標準ライブラリに依存したコードが JS に変換できないことがあり、Scala.js と同じく元のプラットフォームから引き継ぐ問題があるので外した
- Haskell は、GHC の JS バックエンドと WASM バックエンドが未成熟で、出力も重いので外した
- Kotlin/JS は、関数型が主体の言語ではなく、出力も重いので外した
- Roc、Koka、Grain は、研究段階かプレリリースで MoonBit より未成熟なので外した
- Go は WASM の出力サイズが大きいので外した
- Rust は、所有権モデルのためにグラフを扱うコードが書きにくい。また、出力が WASM だけなので、非同期の初期化、バンドラーの設定、SSR や Edge ランタイムでの読み込みの問題を避けられない

TypeScript だけで書く場合は、lint（`let`、引数の再代入、破壊的な配列メソッドの禁止）と型を 1 モジュールに集める構成で関数型スタイルを守る。MoonBit を採らない場合はこちらになる。

### MoonBit が合う点

- ADT、パターンマッチ、イミュータブルな既定値がある。GC があるので、Rust のように所有権モデルのためにグラフを扱うコードが書きにくくなることがない
- JS バックエンドがある。WASM で問題になる非同期の初期化、バンドラーの設定、SSR や Edge ランタイムでの読み込みを避けられる
- レイアウトの計算は外部への依存が少ないので、エコシステムが薄くても困りにくく、言語の表現力の差が書きやすさに表れる

### MoonBit のリスク

- 言語がまだ 1.0 に達していない（0.8 系の時点で検討した）。ベータでコア言語は安定したと宣言されているが、標準ライブラリとツールチェーンは固まっていない。1.0 が出たら見直す
- グラフ、幾何、テストまわりのライブラリは自作になる可能性が高い
- TypeScript との境界で型を二重に持つかどうかは、MoonBit の構造体が JS 側でどう表現されるかと、`.d.ts` を生成できるかで決まる。未確認
- 書ける人が少なく、OSS のコントリビューターを集める障壁になる。コーディングエージェントも TypeScript ほど正確に書けない可能性がある（「試作で確かめること」の 6 で確かめる）

### MoonBit と TypeScript の境界

コアを「データを受け取り、データを返す」純粋関数にし、境界は入力と出力の 2 つの型だけにする。

```
TS: パース → テキスト計測 → [サイズ付きグラフ]
                                ↓
MoonBit (JS バックエンド): 配置・ルーティング・探索（純粋関数）
                                ↓
TS: [座標付きレイアウト] → レンダラー / エディタ
```

リライト元のレイアウト処理からコアの外に出す必要があるものは次のとおり。

- テキスト計測（`engine/text-measurer.ts`）。DOM に触れているのはここだけだった。コールバックで注入せず、TypeScript 側で先に測ってサイズ付きのグラフを渡す。こうすると FFI が要らない
- 探索の `await` と時間予算（`composite/search.ts` の `budgeted(...)`）。時計に依存するので純粋なコアに入れられない。予算を試行回数で数えるか、探索を 1 ステップずつ返してループと打ち切りを TypeScript 側に持たせる
- エディタとのつなぎ込み（`interaction.ts`）は TypeScript 側に残す

SVG の組み立てはレンダラーが TypeScript のテンプレートで行う。レイアウトは幾何データだけを返し、パスも `d` 文字列ではなくセグメント列で返す。

この構成なら、MoonBit をやめてもコアを TypeScript で書き直すだけで済み、境界の型と TypeScript 側のコードはそのまま使える。

### シングルスレッドと WASM 化の性能への影響

MoonBit がシングルスレッドであることは性能の悪化につながらない。

- リライト元で Worker を使うのはサーバーの `apps/server/api/src/services/derivation.ts` だけで、目的はイベントループを止めないことだった。トポロジー 1 件につき Worker を 1 つ立て、その中でレイアウトをシングルスレッドで計算している。MoonBit のコードも Worker の中で動くので、同じ構成を取れる
- 並列化するときは、TypeScript 側で複数の Worker を立て、それぞれで MoonBit のコアを呼ぶ。探索を 1 ステップずつ返す形にしておけば、`composite/search.ts` の候補を並列に評価できる
- ブラウザで共有メモリのスレッドを使うには `SharedArrayBuffer` と COOP/COEP ヘッダーが要る。他人のページに組み込むライブラリでは現実的でないので、Rust を選んでも Worker で分けることになる

WASM 化による高速化にも期待しない。JS バックエンドなら手書きの JS とほぼ同じ速度になると見込む。WASM バックエンドで速くなっても、境界のデータ変換で相殺されうる。リライト元で大きなレイアウトに数分かかっていた原因は探索の計算量だと考えている（未計測）。そうであれば、言語を変えても解決しない。性能は TypeScript と同等とみなして判断する。

### 試作で確かめること

リライト元のレイアウト処理から代表的な一部（`role-tiers` か `route-edges`）を MoonBit に移植し、次を確かめる。

1. JS バックエンドの出力サイズと、TypeScript から呼んだときの API の使い心地
2. 境界の型。`.d.ts` を生成できるか、変換層がどれくらい要るか
3. 純粋なコアとして切り出せるか（テキスト計測と時間予算を外に出せるか）
4. TypeScript で書いた同じ処理との性能比較。JS と WASM のどちらのバックエンドを使うかを決める材料にする
5. 直近のリリースでの破壊的変更の頻度と、追従にかかるコスト
6. コーディングエージェントに書かせたときのコードの品質

### MoonBit 採用の判断基準

「試作で確かめること」の 1〜3 に問題がなく、5 が許容範囲なら MoonBit を採る。そうでなければ TypeScript で書く。
