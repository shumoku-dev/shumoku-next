## 使用言語の選定

レイアウトエンジン、API サーバー（design.md §1.1）、クライアント（SPA）を書く言語を、次の 2 つの構成から選ぶ。どちらの構成でもクライアントは TypeScript で書く。

- 構成 A: すべて TypeScript で書く
- 構成 B: サーバーとコアのドメインロジックを Rust で書く。CLI とライブラリ向けにはコアを WASM にする。TypeScript 側は、Rust が組み立てたシーンを Svelte のコンポーネントで描き、イベントを付けるだけにする

構成 A は、サーバーに Effect を使う A.1 と、valof と Result 型のライブラリを使う A.2 に分けて比較する。どちらを選ぶかと、API フレームワークは未決である。

### 言語選定の動機

リライト元は TypeScript で書かれており、命令的なコードに流れやすく、型定義が分散していた。リライトでは関数型スタイルに寄せる。

レンダラーをアプリに組み込んで mermaid のように使うため、レイアウトエンジンは JS か WASM にコンパイルできる言語で書く必要がある。

リライト元のサーバー（`apps/server/api/src`、テストを除いて約 23,000 行）の中身は、データソースのポーリング、同期ジョブとその計画、観測データの統合、メトリクス、認証、スケジューラーである。状態の遷移、失敗の扱い、並行処理、I/O が絡み、ADT、`Result`、網羅的なパターンマッチといった言語の表現力が役立つ。言語の表現力は、レイアウトエンジンよりサーバーで役立つ。

### リライト元のサーバーで言語の表現力が役立つ範囲

リライト元のサーバーのうち、ADT と網羅的なパターンマッチが最も役立つのは一部である。行数はテストを除いて数えた。

| 部分 | 行数 | 表現力の役立ち方 |
|---|---|---|
| ルートとスキーマ（`modules/`） | 約 5,000 | 入出力の境界のコードで、zod でも serde でもほぼ同じ |
| DB を直接触る 15 ファイル | 約 7,500 | 境界のコードとロジックが混ざっている |
| プラグインのホスト（`plugins/`） | 約 2,700 | 構成 B では wasmtime の制限を使える |
| スケジューラー、同期の計画とジョブ、メトリクスの合成など 9 ファイル | 約 2,800 | 最も役立つ |

リライト元のサーバーには、次の書き方の問題がある。

- サーバーには `try {` が 132 個あり、`switch (` は 2 個しかない
- `services/sync-job.ts` の `SyncJob` は、`state`、`cancelRequested`、`finishedAt?` を別々のフィールドで持ち、完了したのに `finishedAt` がない状態を表せる
- `services/sync-plan.ts` の `SyncJobStep.key` は、ステップの種類を `fetch:<id>` のような文字列で表す

どれも判別可能な union と網羅性チェックで直せる。構成 B との差は、その書き方を言語が強制するか、lint とレビューが強制するかにある。Rust はエコシステム全体が `Result` を返し、変数が既定でイミュータブルである。構成 A では、ライブラリが投げる例外を I/O の境界で包み、`let` や `throw` を lint で禁じる。構成 A を選ぶなら、どのモジュールで何を禁じるかを最初に決め、CI で強制する。

### リポジトリ内の言語の数

リポジトリ内の言語は 2 つまでにする。サーバーとレイアウトエンジンを、TypeScript 以外の別々の言語で書くと、クライアントの TypeScript と合わせて 3 つになる。この理由で、Rust のサーバーと MoonBit のレイアウトエンジンの組み合わせや、Scala か Elixir のサーバー（「サーバーの言語候補から外したもの」）を外した。

プラグインは JavaScript で書いて WASM で動かす（design.md §2）ので、この数には含めない。

### 構成 A: すべて TypeScript

レイアウトエンジンは、lint（`let`、引数の再代入、破壊的な配列メソッドの禁止）と型を 1 モジュールに集める構成で関数型スタイルを守る。TypeScript にも判別可能な union と `never` による網羅性チェックがある。パターンマッチやイミュータブルなデータを簡潔に書くには、ts-pattern や valof などのライブラリを入れるか、`switch` と `readonly` で書く。構成 A.1 でも、純粋な計算をするコアに Effect のランタイムは持ち込まない。

利点:

- 観測データの統合とレイアウトエンジンを、WASM を介さずにサーバー、CLI、ライブラリで共有できる
- WASM のプラグインを Node.js がそのまま実行できる

欠点:

- 関数型スタイルを言語ではなくライブラリで得るので、ADT やパターンマッチは Rust より冗長になる
- Rust よりメモリの消費が大きい

#### 構成 A.1: サーバーに Effect を使う

サーバーには [Effect](https://effect.website/docs/v4/onboarding) を使う。型付きのエラー、依存の注入、並行処理、リトライ、スケジューリング、リソースの解放を同じ書き方で扱える。サーバーなので、ランタイムに残るライブラリのサイズは問題にならない。

利点:

- ポーリングや同期ジョブのエラー処理、リトライ、後始末を共通の仕組みで書ける
- タスクの寿命と、キャンセル時の子タスクの終了やリソースの解放をまとめて管理できる

欠点:

- Effect の実行モデルや依存の注入を学ぶ必要がある
- Promise を返す既存のライブラリと接続するときに、例外を型付きのエラーに変換し、キャンセルや後始末を伝える処理が要る
- レイアウトを計算するコアは Effect に依存させないので、コアとサーバーで書き方が分かれる。コアの書き方は別に定める必要がある

コアとサーバーで書き方をそろえるなら、ドメインの型と純粋な処理はどちらも valof で書き、Effect はサーバーの I/O の組み立てだけに使う。この場合、Effect のデータ型（タグ付きの union や Result 型）と valof の役割が重なるので、ドメインの型を valof で書くという規則が要る。コアが返す Result は、サーバーで Effect の値に変換する。

API フレームワークの候補は Effect の [HttpApi](https://effect.website/docs/v4/api/effect/http-api/HttpApi) と [RPC](https://effect.website/docs/v4/api/effect/rpc/RpcServer) である。通常の HTTP API と OpenAPI を提供するなら HttpApi が合う。SPA とサーバーの通信を Effect の型付きクライアントでそろえるなら RPC が候補になる。Effect の採用だけでは API の形式は決まらず、Hono のハンドラーから Effect の処理を呼ぶ構成も取れる。

参照した資料は Effect 4.0.2 のもので、HttpApi と RPC は unstable として公開されている。採用するバージョンと API の安定性は、実装の前に確かめる。ただし、安定性は構成 A.1 と B の差にならない。構成 B でも、wasmtime は毎月メジャー版を上げて API を変え（49 系の時点で確かめた）、axum は 1.0 に達していない（0.8 系の時点で確かめた）。

#### 構成 A.2: valof と Result 型のライブラリを使う

valof（[jo16oh/valof](https://github.com/jo16oh/valof)）では、ドメインロジックをプレーンなデータとコンパニオンオブジェクトで書く。クラスは使わない。ブランド付きのイミュータブルな型と、網羅的な `match` を持つ `Enum` を提供し、任意の Result 型のライブラリと組み合わせられる。依存がなく 852 B（gzip）から使えるので、レイアウトエンジンでも同じ書き方ができる。

非同期処理は Promise、AbortController、同時実行数を制限するキューなどで書く。リトライやスケジューリングは、小さなヘルパーを自分で書くか別のライブラリで補う。依存は関数の引数などで渡す。

利点:

- コアとサーバーでドメインロジックの書き方をそろえられる
- 通常の async/await と Promise を使い、必要な非同期処理だけを追加できる
- 依存が薄いので、安定性で最も有利である。Hono は 4 系で長く安定しており（4.13 系の時点で確かめた）、valof と Result 型のライブラリは薄く、問題があれば差し替えやすい

欠点:

- タスクの寿命、キャンセル、リトライ、後始末を統一するルールとヘルパーを用意する必要がある
- Result を返す処理と例外を投げる処理が混在しないように、I/O を呼ぶ箇所で例外を Result に変換する必要がある

API フレームワークの候補は [Hono](https://hono.dev/) である。リライト元も Hono と `@hono/zod-openapi` を使っており、HTTP API と OpenAPI を提供する構成を引き継ぎやすい。

#### 構成 A の並行処理の要件

リライト元のサーバーで必要な並行処理は、主に次のものである。

- 複数のデータソースを並行して取得し、個別の失敗を集める
- ポーリングの重複を防ぎ、全体の同時実行数を制限する
- 同期ジョブをキャンセルし、終了時にタイマーやリソースを解放する
- レイアウト計算を Worker で動かし、タイムアウト時に終了する

これらは構成 A.2 でも扱える範囲であり、Effect の Fiber を使った高度な並行処理は必須ではない。タイマー、リトライ、同時実行数の制限は、Promise を包む小さなユーティリティ関数で書ける。

HTTP 応答後も続く同期ジョブは、リクエストとは別に寿命を管理する。

#### 同時実行数の制限とキャンセルはプラグインのホストに閉じる

サーバーが外部に問い合わせる経路は、プラグインと、サーバーに組み込まれた SNMP の読み取り（リライト元の `discovery/deep-read.ts` と `discovery/snmp-client.ts`）である。ほかに時間がかかる処理はレイアウトの計算だけで、Worker で動かす。同時実行数の制限、タイムアウト、キャンセルは、アプリケーション全体ではなく、外部に問い合わせる箇所とレイアウトの Worker で扱えば足りる。

リライトで SNMP の読み取りをサーバーに組み込むか、プラグインに移すかは決めていない。サーバーに組み込むなら、SNMP のクライアントにも同時実行数の制限とタイムアウトが要る。

リライト元が同時実行数を制限しているのは次の箇所である。理由はコードに書かれていないが、データソースに負荷を集中させないことと、QuickJS をメインスレッドで動かすサーバーのイベントループを止めず、メモリを使い切らないことだと推測している。

- `services/poll-scheduler.ts`: ポーリングを全体で 3 つまでに制限する。トポロジーごとのタイマーから発火するので、待ち行列を持つ
- `services/health-checker.ts`、`services/link-automap.ts`、`services/topology.ts`: 配列を最大 N 個ずつ処理する

プラグインのホストは、次の形にする案を考えている。

- ホストは、データソースごとの同時実行数の制限、タイムアウト、Worker の起動と `terminate()`、ホストの `fetch` の abort を内側に持つ。呼ぶ側は Worker もセマフォも知らない
- 同時実行数の上限は、全体に 1 つではなくデータソースごとに掛ける。別々のデータソースを見るポーリングは互いに待たせなくてよい
- ポーリングは、トポロジーごとのループが「セマフォを取る、ポーリングする、返す、次の間隔まで待つ」を繰り返す。リライト元の待ち行列と `inFlight`、`queued` のフラグは要らなくなる
- `AbortSignal` はホストの内部の実装に閉じる。外からキャンセルされた呼び出しは、終わるかタイムアウトするまで止めずに待ち、呼ぶ側が結果を捨てる。リライト元の同期ジョブと同じ扱いである。サーバーの終了時は、ホストの `dispose()` で Worker をまとめて止める
- タイムアウトを長く取るプラグインで、キャンセルした後も動き続けるのが困るとわかったら、ホストの関数に `signal` の引数を足す

#### 構成 A.1 と A.2 の比較

構成 A.2 に傾いている。Effect の利点が役立つ範囲が狭く、学習と実装の負担に見合わないと見ている。

- Effect が最も役立つのは、長く動く処理の寿命の管理である。リライト元では `poll-scheduler.ts`、`sync-scheduler.ts`、`sync-job.ts`、`health-checker.ts`、`derivation.ts`、`signal-streams.ts` の約 1,700 行が当たる。一方、Effect を返す関数は呼ぶ側も Effect で書くので、サーバー全体が Effect の書き方になる
- Effect の利点の多くは、標準の機能で代えられる。リソースの後始末は `using` と `DisposableStack`、タイムアウトとキャンセルの組み合わせは `AbortSignal.timeout()` と `AbortSignal.any()`、部分的な失敗の収集は `Promise.allSettled`、依存の注入は AsyncLocalStorage を包んだ仕組み（「構成 A.2 での依存の注入」）、型付きのエラーは Result 型で書ける
- キャンセルが子タスクへ自動で伝わる点は、標準の機能で代えられない。ただし、Fiber の中断は Worker の中で動く QuickJS やレイアウトの計算には届かない。中断されたら Worker を `terminate()` し、ホストの `fetch` を abort する処理は、構成 A.1 でも自分で書く。キャンセルしたい対象はどちらも Worker の中にあるので、この利点が役立つ場所がほとんど残らない
- 状態を表す型の網羅性は、どちらでも valof の `Enum` で書くので差がない。Effect が型で強制するのは、エラーの扱い、依存、リソースである
- Effect は実行モデルが async/await と違い、サーバーに貢献するのに学習が要る。コーディングエージェントが古い版（v3）の API で書くおそれもある

構成 A.2 では、寿命の管理を次の規則で守る。

- タイマー、同時実行数の制限、リトライは 1 つのモジュールのユーティリティ関数にまとめ、それ以外では `setTimeout`、`setInterval`、`new Promise` を lint で禁じる。リライト元では `setTimeout` と `setInterval` が 29 か所に散らばっている
- `no-floating-promises` を有効にする
- 時計と `sleep` を外から注入できるようにし、時間に依存するテストを決定的に書く

#### 構成 A.2 での依存の注入

構成 A.2 では、サーバーのロジックをサービスにまとめる。コアは状態を持たないドメインロジックで、サービスは状態（DB の接続、実行中の同期ジョブの一覧など）を持つドメインロジックである。サービスは、サービスを作る関数（`createRepository(connection)` など）が返すオブジェクトである。サービスはサーバーだけで使い、ブラウザでも動かすコアには持ち込まない。

起動時にすべてのサービスを作り、`registerService(Repository, repository)` でコンテキストに登録する。使う側は `useService(Repository)` で取り出す。`Repository` のように `useService` に渡すものをタグと呼ぶ。タグは、コンテキストからサービスを取り出すときのキーにするオブジェクトで、サービスのモジュールで `defineService<Repository>('Repository')` のように定義する。サービスの型は、`type Repository = ReturnType<typeof createRepository>` のように、サービスを作る関数の戻り値から導出する。型推論が循環するサービスと、本番用の実装が複数あるサービスでは、型を手で書く。

コンテキストは、依存を引数で何段も渡して回らずに済ませるために使う。

- 1 つのサービスだけが使う依存（DB の接続など）は、サービスを作る関数の引数で渡し、コンテキストには入れない
- サービスが他のサービスを使うときは、引数で受け取らず、メソッドが呼ばれるたびに `useService` で取り出す。サービスの外の関数も同じように取り出す。サービスを取り出す経路は `useService` だけにする
- コンテキストに入れるのはサービスだけにする。リクエストごとの値（利用者、リクエスト ID）は、それを扱うサービス（`Auth`、`Logger`）が内側に持つ。使う側は `useService(Auth).principal()` のようにメソッドで読む
- 登録し忘れは起動時に検査する。`defineService` は定義したタグを記録し、起動時に呼ぶ `assertAllRegistered()` は、登録されていないタグがあればエラーにする
- サービス同士を引数で渡さないので、作る順序を気にしなくてよい。Effect の Layer のような順序の自動解決は要らない
- 可変の状態は、サービスを作る関数の中に持ち、モジュールレベルには置かない。リライト元では、モジュールレベルの `Map` やクラスのフィールドに散らばっていた
- 終了時の後始末は、`await using` か `AsyncDisposableStack` で書く

AsyncLocalStorage は 1 つだけ使い、依存の注入の仕組みを実装するモジュールだけが触る。ストアの中身は、キーから値へのイミュータブルなマップにする。

- サービスは、タグをキーにしてこのマップに入れる
- リクエストごとの値を持つサービスは、同じモジュールが提供する `createVariable<Principal>()` で変数を作る。変数は `run(value, fn)` と `get()` を持ち、`run` はエントリを足したマップで `fn` を実行する。TC39 の AsyncContext の提案にある `AsyncContext.Variable` と同じ形である
- 起動時のマップを取っておき、そのマップで関数を実行する関数を用意する。長く動く処理を始めるときに使う（「構成 A.2 での認証と認可」）

テストでは、使うサービスだけをテスト用の実装で登録し、`assertAllRegistered()` は呼ばない。登録していないサービスを `useService` で取り出すとエラーになる。1 つのサービスだけを試すテストでは、サービスを作る関数にテスト用の依存を引数で渡す。

サービスのメソッドは、TypeScript も Knip も未使用を検出しない。サービスの登録し忘れが起動時にわかることと、サービスの単位で差し替えられることを優先して、未使用を検出できないことを受け入れる。

次の案は採らない。

- モジュールに並べた関数を `import * as Database from './database.ts'` のように名前空間としてインポートし、関数が呼ばれるたびに DB の接続などをコンテキストから取り出す案。Knip が未使用の関数を報告する（6 系のドキュメントで確かめた）。1 つのモジュールしか使わない依存までコンテキストに入れることになる。途中の関数をテストで差し替えるには、関数ごとにタグが要る
- すべてのサービスを 1 つのオブジェクトにまとめ、型を付けてコンテキストに渡す案。登録し忘れがコンパイルエラーになる。テストでも全サービスを渡すか、一部だけを重ねる関数を別に用意する必要がある。全サービスの型は、手で書くか、`typeof` で導出する。導出すると、サービス同士が互いのメソッドを呼ぶときに型推論が循環するおそれがある（確かめていない）
- サービスを valof の Trait で書く案。第 1 引数を使わないメソッドを Trait に並べ、空の Val に実装し、`dyn` でメソッドの形で呼ぶ。valof の linter（`unused-member`）が未使用のメンバーを報告する。未使用検出のためだけに、Trait と Val を本来の用途と違う形で使うことになる
- サービスも引数で渡す案。型で検査されるが、深い階層の関数まで引数で渡して回ることになる。引数と `useService` の両方で取り出せるようにすると、テストでは両方に同じ実装を入れる必要がある
- サービスを作る関数の冒頭で `useService` を呼び、メソッドではクロージャで使う案。サービスを作る順序を起動時のファイルに手書きする必要がある
- `useService` を呼べる場所を命名規約で制限する案。`useService` を呼ぶ関数とそれを呼ぶ関数すべてに名前を付ける規約は、名前の制約が、呼び出し元をさかのぼったすべての関数に及び、引数で渡して回るのと同じ手間になる
- valof のコンパニオンオブジェクトに依存を持たせる案。コンパニオンはモジュールレベルの定数なので、書き込んだ依存がグローバルな状態になる。依存を受け取って関数群を返すメンバーにしても、純粋な関数と I/O が同じ名前の下に混ざり、コアと共有する型にサーバーの依存の型が入る
- `defineService` にサービスを作る関数も渡し、タグと実装を 1 つにまとめる案。サービスの型を実装から推論できるが、`ReturnType` で導出すれば同じことができ、`defineService` に実装を渡す仕組みが要らない
- 取り出す関数を `inject`、登録する関数を `provide` と名付ける案（Vue と Angular の名前）。取り出す側は注入されたものを受け取るので、`inject` は語の向きが逆である

#### 構成 A.2 での認証と認可

認可は Hono のミドルウェアで判断し、認証した利用者は `Auth` サービス（「構成 A.2 での依存の注入」）が持つ。

- 認可の判断はルートの層で行う。ルートの定義ごとに必要な権限を書き、ミドルウェアが確かめる。権限を書かないルートは定義できないようにし、既定で拒否にする
- ミドルウェアは、解決した利用者を `useService(Auth).runAs(principal, next)` でリクエストごとに入れる。サーバーの関数は `useService(Auth).principal()` で読む。利用者は Hono のコンテキスト（`c.var`）には置かず、置き場所を 1 つにする
- リライト元の認可は、ロールと 3 つの権限（`workspace:read`、`workspace:write`、`admin:manage`）で判断し、リソースごとの所有者を見ない（`apps/server/api/src/auth/`）。サーバーの関数が利用者を読むのは、当面、監査ログくらいである
- リライト元は、必要な権限をパスの正規表現で決めている（`auth/access-policy.ts` の `ADMIN_SURFACES`）。管理用のルートを新しいパスに足して正規表現への追加を忘れると、`workspace:write` の権限だけで呼べる。ルートの定義に権限を書くのは、これを防ぐためである

リクエストの外で動く処理には、次の扱いが要る。

- ポーリングのループや定期的な同期には利用者がいないので、そこから呼ばれた関数では `principal()` が `undefined` を返す。バックグラウンドの処理にシステムを表す利用者を入れるか、バックグラウンドからも呼ばれる関数では利用者を読まないことにするかは、決めていない
- AsyncLocalStorage のコンテキストは、その中で始めた非同期の処理に引き継がれる。HTTP の応答後も続く同期ジョブは、始めたリクエストの利用者を持ったまま動く。監査ログに残す利用者としては、ジョブを始めた利用者が正しい
- リクエストをきっかけに、トポロジーのポーリングのループのような共有の長く動く処理を始めると、きっかけを作った利用者がその処理に残る。長く動く処理を始める関数では、コンテキストを起動時のものに入れ直す。依存の注入の仕組みに、起動時のコンテキストで関数を実行する関数を用意する

#### AsyncLocalStorage のコンテキストの引き継ぎ

サーバーの起動を `run()` の中で行ったとき、後から届くリクエストのハンドラーにコンテキストが引き継がれるかは、ランタイムと HTTP サーバーの実装による（確かめていない）。リクエストごとの値（利用者、リクエスト ID）は、ミドルウェアでリクエストごとに変数の `run()` で包む。サービスも同じコンテキストから取り出すので、引き継がれないなら、ミドルウェアがリクエストごとに起動時のコンテキストに入り直す。

### 構成 B: サーバーとコアのドメインロジックを Rust

サーバーと、レイアウトエンジン、観測データの統合、描画するシーンの組み立てといったコアのドメインロジックを Rust で書く。サーバーはコアのクレートをネイティブのライブラリとしてリンクするので、サーバーとコアの間には WASM も JSON も要らず、型を共有できる。CLI とライブラリ向けには同じクレートを WASM にする。TypeScript 側は、シーンを Svelte のコンポーネントで描き、イベントを付けることだけを受け持つ（design.md §1.2）。

利点:

- サーバーのロジックで役立つ表現力（ADT、`Result`、網羅的なパターンマッチ）が言語に組み込まれている
- wasmtime をプラグインのホストにでき、プラグインの実行時間とメモリを QuickJS とは別に WASM の層で制限できる（「wasmtime によるプラグインの実行の制限」）
- 単一のバイナリで配れ、メモリの消費が小さい

欠点:

- CLI とライブラリ向けに、コアとの間に WASM の境界ができる
- DB のアクセスが構成 A より書きにくい（「構成 B での DB のアクセス」）
- 非同期 Rust が複雑
- コンパイルに時間がかかる
- 学習コストが TypeScript より高い

利点のうち次の 2 つは、構成 A との差が小さい。

- 単一のバイナリは、構成 A でも `bun build --compile` や Node.js の SEA で作れる。差はバイナリのサイズとメモリの消費で、小さな VM や Raspberry Pi で動かす利用者をどれだけ重く見るかで評価が変わる
- プラグインの実行時間は、構成 A でも VM を Worker で動かせば同じ深さで守れる（「wasmtime によるプラグインの実行の制限」）。差はメモリの上限の掛けやすさと、Worker を立てるコストである

欠点のうち学習コストは最初に払えば済むが、WASM の境界、ネイティブと WASM の結果の一致、2 つのツールチェーン、sqlx のキャッシュ、コンパイル時間は保守のあいだ続く。コンパイル時間は、結果を見ながら何度も調整するレイアウトのヒューリスティックの作業で、影響が最も大きい。

レイアウトエンジンを Rust で書くときの問題は、次のように対処する。

- 所有権モデルのためにグラフを扱うコードが書きにくい問題は、ノードやポートを `NodeId(u32)` のような ID で参照し、レイアウトの各段を新しい出力を返す関数にすれば軽くなる。構造を共有したいときは、型にライフタイムが出る `Cow<'a, T>` より、`Rc::make_mut` / `Arc::make_mut` か永続データ構造の `im` クレートを使う
- CLI とライブラリとの境界の型は、`tsify` と `serde-wasm-bindgen` で `.d.ts` を生成して渡す。serde のタグ付きの `enum` は判別可能な union になる
- ブラウザでは WASM になるので非同期の初期化が要る。ただし mermaid の `render()` も非同期なので、組み込む側の使い勝手は変わらない
- バンドラーの設定は、WASM を JS に埋め込めば要らない。その代わりサイズが 3 割ほど増える

#### wasmtime によるプラグインの実行の制限

構成 B では、wasmtime をプラグインの WASM のホストにする。epoch interruption か fuel で実行時間を、`ResourceLimiter` でメモリを、QuickJS とは別に WASM の層で制限できる。

リライト元は、QuickJS をサーバーのメインスレッドで動かし、実行時間の上限を QuickJS の `interruptHandler` だけで守っている（`apps/server/api/src/plugins/sandbox/quickjs-vm.ts`）。QuickJS のバグで割り込みの確認が実行されないと、サーバーのイベントループごと止まる。構成 A で実行時間について同じ深さの防御を得るには、VM を Worker で動かし、時間切れで `terminate()` する。

wasmtime の Component Model でホストとのインターフェースを型付きで定義できる点は、ほとんど差にならない。プラグインは JavaScript で書き、ホストと QuickJS の間のインターフェースは内部のもの（design.md §2.2）なので、型付きの定義が役立つのは内部の実装だけである。

#### 構成 B でサーバーと CLI のレイアウトを一致させる

サーバーと CLI で同じレイアウトを出す（design.md §1.3）には、構成 B ではコアのネイティブのビルドと WASM のビルドで結果を一致させる必要がある。

- Rust の `HashMap` と `HashSet` の反復順は、ネイティブではプロセスごとに変わる。JS の `Map` と `Set` は挿入順なので、リライト元のコードをそのまま移すと、結果が実行ごとに変わる。コアでは `IndexMap` か `BTreeMap` を使い、clippy の `disallowed_types` で `HashMap` と `HashSet` を禁じる
- リライト元のレイアウトは `Math.hypot` を使っている。Rust の `f64::hypot` は、ネイティブと wasm32 で同じ実装が使われる保証がなく、最後のビットがずれうる。`libm` クレートを使うか、`sqrt(dx * dx + dy * dy)` で計算する。`sqrt` は IEEE 754 で正しく丸めることが決まっているので、どの環境でも同じ値になる

- リライト元のレイアウトが使う浮動小数点の関数は `Math.hypot` と `Math.sqrt` だけである。この状態を保つため、clippy の `disallowed_methods` で `sin` などの超越関数を禁じる
- 一致が崩れたことを検出するため、同じ入力をネイティブと wasm32 で計算し、出力をビット単位で比べるテストを CI に置く

構成 A でも、サーバーと CLI で JS エンジンが違えば（Bun の JavaScriptCore と Node.js の V8 など）、`Math.hypot` の結果が一致する保証はない。ECMAScript は `Math.hypot` の精度を実装に任せている。

#### 構成 B での DB のアクセス

DB のアクセスは構成 A の方が書きやすい。構成 A では、Kysely を使えば条件を組み立てるクエリにも型が付く。構成 B で使う sqlx には次の問題がある（sqlx 0.9 系と Kysely 0.29 系の時点で確かめた）。

- sqlx の `query!` が検査するのは、文字列リテラルで書いた固定の SQL だけである。一覧の絞り込みのように条件を組み立てるクエリは `QueryBuilder` で書くが、SQL も結果の型も検査されない。Diesel なら組み立てるクエリにも型が付くが、ジェネリクスが重く、コンパイル時間とエラーメッセージが sqlx より悪くなる
- `query!` はコンパイル時に DB に接続するか、`cargo sqlx prepare` で作ったキャッシュを使う。キャッシュを CI で最新に保つ手間が加わり、マクロの分だけコンパイルも遅くなる
- Rust は型を名前で区別するので、行の構造体からドメインの型への詰め替えが要る。構成 A でも valof のブランド付きの型を使えば変換は要るが、Kysely ではテーブルの型の定義にブランド付きの型を直接書けるので、詰め替えを省ける

DB のアクセスは境界のコードなので、Rust の表現力（ADT、網羅的なパターンマッチ）がほとんど役立たない。リライト元のサーバーでは、DB を直接触るファイルがテストを除いて 15 個ある（`getDatabase()` か `.prepare(` を呼ぶもの）。

#### 構成 B の並行処理の要件

「構成 A の並行処理の要件」に挙げた 4 つの要件は、構成 B では次のように満たす。

- 複数のデータソースの並行した取得と、個別の失敗の収集は、tokio の `JoinSet` で書く
- ポーリングの重複は実行中のデータソースの集合で防ぎ、全体の同時実行数は `Semaphore` で制限する
- 同期ジョブのキャンセルは `CancellationToken` で伝え、タイマーやリソースは `Drop` で解放する。キャンセルは future の drop で起きるので、`select!` などで `await` の途中で drop されても状態が壊れない書き方にする
- レイアウトの計算は別のスレッドで動かす。スレッドは外から止められないので、タイムアウトしたらコアが自分で計算を打ち切る。「レイアウトエンジンの境界」の、予算を試行回数で数えるか探索を 1 ステップずつ返す設計が必須になる。構成 A では、Worker を `terminate()` すれば外から止められる

#### 構成 B での観測データの統合の WASM

構成 B では、観測データの統合（design.md §1.4）をレイアウトエンジンと同じく Rust で書き、CLI 向けに WASM にする。mermaid のように組み込むライブラリにはレイアウトエンジンだけを含め、`resolve()` は CLI だけが読み込むように、WASM のモジュールを分ける。

### レイアウトエンジンの境界

どちらの構成でも、レイアウトエンジンのコアを「データを受け取り、データを返す」純粋関数にする。構成 B では、コアをすべて Rust で書くことになる。
```
TS: パース → テキスト計測 → [サイズ付きグラフ]
                                ↓
コア: 配置・ルーティング・探索（純粋関数）
                                ↓
コア: [座標付きレイアウト] → シーンの組み立て
                                ↓
Svelte: [シーン] → SVG の要素
```

リライト元のレイアウト処理からコアの外に出す必要があるものは次のとおり。

- テキスト計測（`engine/text-measurer.ts`）。DOM に触れているのはここだけだった。測り方は「テキストの幅の計測」で決める。コアの外で測るなら、コールバックで注入せず、TypeScript 側で先に測ってサイズ付きのグラフを渡す。こうすると FFI が要らない
- 探索の `await` と時間予算（`composite/search.ts` の `budgeted(...)`）。時計に依存するので純粋なコアに入れられない。予算を試行回数で数えるか、探索を 1 ステップずつ返してループと打ち切りを呼び出し側に持たせる

どちらの構成でも、シーンの組み立てまでをコアで行い、Svelte のコンポーネントが描く（design.md §1.2）。レイアウトは幾何データだけを返し、パスも `d` 文字列ではなくセグメント列で返す。

### レイアウトエンジンの性能

- リライト元で Worker を使うのはサーバーの `apps/server/api/src/services/derivation.ts` だけで、目的はイベントループを止めないことだった。トポロジー 1 件につき Worker を 1 つ立て、その中でレイアウトをシングルスレッドで計算している。どちらの構成でも同じ形を取れる
- 並列化するときは、複数の Worker を立て、それぞれでコアを呼ぶ。探索を 1 ステップずつ返す形にしておけば、`composite/search.ts` の候補を並列に評価できる
- ブラウザで共有メモリのスレッドを使うには `SharedArrayBuffer` と COOP/COEP ヘッダーが要る。他人のページに組み込むライブラリでは現実的でないので、構成 B でも Worker で分ける

言語による高速化には期待しない。WASM で速くなっても、境界のデータ変換で相殺されうる。リライト元で大きなレイアウトに数分かかっていた原因は探索の計算量だと考えている（未計測）。そうであれば、言語を変えても解決しない。

### 試作で確かめること

リライト元のレイアウト処理から代表的な一部（`role-tiers` か `route-edges`）を Rust に移植し、TypeScript で書いた同じ処理と比べる。

1. WASM の出力サイズと、TypeScript から呼んだときの API の使い心地
2. 型の生成の精度。JSON Schema（design.md §3.2）から生成した Rust と TypeScript の型で、`oneOf` と判別子が Rust の `enum` と TypeScript の判別可能な union になるか。レイアウトエンジンの境界の型を Rust で定義するなら、`tsify` が生成する `.d.ts` の精度
3. 純粋なコアとして切り出せるか（テキスト計測と時間予算を外に出せるか）
4. TypeScript 版との性能比較
5. コーディングエージェントに書かせたときのコードの品質

レイアウトの試作で測るのは構成 B のコストであり、読みやすさは比べない。所有権のためにグラフを ID で参照し、値を明示的に複製する分、レイアウトのコードは Rust の方が読みにくくなるのが明らかなためである。Rust の表現力（所有権による変更の制限、網羅性の検査）はレイアウトでも役立つが、構成 B を選ぶ理由になるのはサーバー側の利点である。

読みやすさは、サーバーの同期ジョブの試作だけで比べる。構成 A.2 と B で同じ処理を書き、並列取得、部分失敗、キャンセル、保存、後始末まで含めて、読みやすさと実装の負担を比べる。

構成 A.2 では、プラグインのホストの境界（「同時実行数の制限とキャンセルはプラグインのホストに閉じる」）を試作し、次を確かめる。どちらも満たせれば、構成 A.1 との比較の試作は省く。

1. タイムアウトしたプラグインとサーバーの終了時に、Worker と進行中の `fetch` が確実に片付くか
2. データソースごとの上限と Worker の数の上限を、ホストの中だけで扱えるか

構成 A では、リライト元の core のテスト（約 9,400 行）のフィクスチャと期待値を、書き直しのあいだ回帰の基準として使いやすい。構成 B では、テストを Rust に移すか、JSON のゴールデンファイルに変える。

### 構成の判断基準

構成 A.2 に傾いている。Rust の表現力が最も役立つ範囲（「リライト元のサーバーで言語の表現力が役立つ範囲」）に比べて、構成 B の欠点がかかる範囲が広いためである。

- 構成 B は、試作の結果に加えて、サーバーのロジックを Rust で書く利点が、Rust の欠点に見合うかで決める。次のどれかが当てはまれば構成 B に傾く
  - 保守の中心になる人が、TypeScript より Rust の方が速く書ける
  - 同期ジョブの試作で、構成 A.2 が構成 B と同じ保証（状態遷移の網羅、例外の封じ込め、キャンセル時の後始末）を得るのに、多くのユーティリティ関数や lint の規則が要る
  - 小さなマシンでのメモリの消費が、利用者にとって重要だとわかる
- 構成 B を採らなければ、構成 A.2 にする（「構成 A.1 と A.2 の比較」）。プラグインのホストの試作で、ユーティリティ関数が Effect の Schedule、Semaphore、Scope を作り直す規模になるなら、構成 A.1 を見直す
- 保守する人と貢献者が誰かを確かめる。リライト元の作者とプラグインを書くネットワークエンジニアは TypeScript を書いてきた。構成 B ではサーバーとコアへの貢献に Rust が要り、構成 A.1 では Effect の学習が要る

### レイアウトエンジンの言語候補から外したもの

JS か WASM にコンパイルできる言語を候補にし、TypeScript と Rust 以外は次の理由で外した。MoonBit は design.md §3.1「却下: レイアウトエンジンのコアだけを MoonBit で書く」で却下した。

- Elm は、JS から関数として呼べないので外した。JS とのやり取りは非同期の ports に限られ、同期の `layout(graph)` を提供できない。0.19.1 からリリースも止まっている
- PureScript はエコシステムと成熟度で外した
- Scala.js は、TypeScript との境界の型を扱いにくいので外した。Scala 3 で `.d.ts` を生成する道具がなく（sbt-scala-ts は Scala 2 系だけに対応する）、型を TypeScript 側で定義して ScalablyTyped で取り込むしかない。Scala 3 の高い表現力（型クラス、高カインド型など）も、純粋な計算のコアでは要らない
- Gleam は型の表現力が低く、制約を強めた TypeScript と大差ない。エコシステムもないので外した
- ReScript は、MoonBit と同じく表現力が役立つのがレイアウトエンジンだけなので外した（design.md §3.1「却下: レイアウトエンジンのコアだけを MoonBit で書く」）。境界の型（`genType` による `.d.ts` の生成）と安定性が確かめられている点は MoonBit より有利だった
- OCaml（Melange / wasm_of_ocaml）は、ツールチェーン（dune、opam、Melange、JS のバンドラー）が重いので外した
- F#（Fable）は、.NET の標準ライブラリに依存したコードが JS に変換できないことがあり、Scala.js と同じく元のプラットフォームから引き継ぐ問題があるので外した
- Haskell は、GHC の JS バックエンドと WASM バックエンドが未成熟で、出力も重いので外した
- Kotlin/JS は、関数型が主体の言語ではなく、出力も重いので外した
- Roc、Koka、Grain は、研究段階かプレリリースで MoonBit より未成熟なので外した
- Go は WASM の出力サイズが大きいので外した

### サーバーの言語候補から外したもの

Scala と Elixir は、サーバーの言語としては悪くないが、リポジトリ内の言語が 3 つになるので外した（「リポジトリ内の言語の数」）。どちらもレイアウトエンジンを書けないため、レイアウトエンジンを書く言語が別に要る。

- Scala 3（JVM）: 型付きの副作用を扱うライブラリ（ZIO、Cats Effect）が最も成熟しており、型クラスや高カインド型といった表現力がサーバーのロジックで役立つ。WASM のプラグインは Chicory（Bytecode Alliance に移って Endive になった。QuickJS を動かす実績がある）で動かせる。長く動き続けるプロセスなので、JVM の起動時間やメモリの消費は大きな差にならない
- Elixir: BEAM はプロセスごとにヒープが分かれ、プリエンプティブにスケジュールされるので、プラグインだけでなくホスト自身のコードにバグがあっても、そのプロセスだけが落ちて全体は止まらない。スーパーバイザーが落ちたプロセスを再起動する。WASM は Wasmex（wasmtime を Rust の NIF として組み込んだライブラリ。Component Model に対応）で動かせる。ただし NIF の中でネイティブのコードがクラッシュすると BEAM 全体が落ちる。イミュータブルが基本なので、型が弱くても共有された状態に不整合が生じる種類のバグは起きにくい。型システムは、v1.20 で型推論による段階的な検査が入ったが、利用者が型を定義する手段はまだない（型付きの構造体は v1.21、型シグネチャは v1.22 で予定されている）

ほかに次の言語を外した。

- F#（.NET）は、構文のなじみやすさとエコシステムで Scala に劣るので外した。WASM のホストは公式の wasmtime-dotnet があり、Scala より素直である
- Kotlin（JVM）は、関数型が主体の言語ではないので外した。関数型に寄せるなら Scala を選ぶ
- Haskell は、ツールチェーンが重く、書ける人が少ないので外した
- OCaml は、ツールチェーンが重いので外した。wasmtime のバインディングも 0.0.3（wasmtime v0.22 に対応）で止まっており、WASM のホストとして弱い
- Gleam は、型の表現力が低いので外した。BEAM の並行処理はポーリングに向いている
- Go は、ADT がなく、関数型スタイルに寄せる動機に合わないので外した
- MoonBit（ネイティブ）は、サーバー向けのエコシステム（HTTP、DB、認証）がほとんどないので外した

プラグインが落ちても全体が止まらない隔離は、どの言語でも WASM のサンドボックスで得られる。wasmtime では、プラグインの trap はホストにエラー値として返り、メモリと実行時間に上限をかけられる。落ちた後の再起動は、Rust なら tokio のタスクの監視かアクターのライブラリ（ractor など）で書く。

## リポジトリの構成

モノレポにするか、リポジトリを分けるかを決める。モノレポの方が合っていると考えている。リライト元の作者はモノレポをやめたがっているので、その理由を聞いてから決める。

### モノレポが合う理由

- モデルを複数のパッケージで共有する。YAML のスキーマを JSON Schema だけで定義し、TypeScript の型を生成する（design.md §3.2）。スキーマを変えると、SPA、サーバー、CLI、ライブラリが一度に変わる。モノレポなら 1 つのコミットで変更してまとめてテストできる。リポジトリを分けると、スキーマのパッケージを公開してから各リポジトリで追従する手順になり、その間は版がずれる
- レイアウトエンジンの境界の型を共有する。構成 B（「使用言語の選定」）で境界の型を Rust で定義するなら、Rust の型から `.d.ts` を生成して TypeScript 側で使う。生成元と使う側が同じリポジトリにあれば、型の食い違いを CI で検出できる
- ドキュメントと LP も、ライブラリの同じ版で図を描ける。ドキュメントの例をワークスペースのレンダラーで描けば、例がそのままレンダラーのテストになる。テーマ（配色やフォント）も、アプリ、ドキュメント、LP で 1 つの定義を共有できる
- CI は最適化できる。変更されたパッケージとそれに依存するものだけをビルドしてテストする仕組みは Turborepo などにある。パスでの絞り込みやリモートキャッシュも使える

### リポジトリを分ける理由になりうること

リライト元の作者がモノレポをやめたい理由はまだ聞いていない。よくある理由と、モノレポでの対処を挙げる。

- リリースの流れを独立させたい。リライト元はモノレポのまま、成果物ごとに独立した版でリリースしており（リライト元の `docs/releasing.md`）、モノレポでも両立する
- CI が遅い。「モノレポが合う理由」の CI の最適化で対処できる
- ライセンスを分けたい。リライト元のコードは AGPL である。ドキュメントや LP を別のライセンスにするなら、ディレクトリごとにライセンスを置けば済む
- 権限や担当を分けたい。担当は CODEOWNERS で表せる。リポジトリへの書き込み権限まで分けたいなら、リポジトリを分ける理由になる
- 言語が混ざる。構成 B では Rust と TypeScript が同居するが、Cargo のワークスペースと bun のワークスペースは 1 つのリポジトリに共存できる

## パッケージの分割

構成 A.2（「使用言語の選定」）を選ぶ場合の、モノレポのワークスペースの分け方と、npm に公開するパッケージを決める。モノレポにするかどうかは「リポジトリの構成」で決める。次の構成に傾いている。

```
libs/core/        private
libs/renderer/    公開（@shumoku/renderer）
libs/catalog/     private
apps/cli/         公開（@shumoku/cli）
apps/hub/         private
apps/drafter/     private
apps/docs/        private
```

依存の向きを次のように制限する。

- `libs/core` は、ほかのワークスペースのパッケージに依存しない
- `libs/renderer` と `libs/catalog` は `libs/core` に依存する
- `apps/*` は `libs/*` に依存する。`libs/*` は `apps/*` に依存しない
- `libs/renderer` は `libs/catalog` に依存しない

### 製品の名前

パッケージとディレクトリの名前は、次の製品の名前に合わせる。

- shumoku: ファイル形式と、そのレンダラーの名前。mermaid と同じ使い方である
- Shumoku Hub: リライト元の server に当たる。複数のデータソースから集める場所という意味で Hub にする
- Shumoku Drafter: リライト元の editor に当たる。この名前は合意が取れている

Hub のほかに、次の名前を検討した。

- Collector は、OpenTelemetry Collector のように、集めて転送するだけで画面を持たないエージェントに見える
- Nexus は Cisco のスイッチの製品名、Central は Aruba Central と重なる
- Atlas は、集まった図を見る場所という意味になり、データソースから集める意味が弱い
- Server は誤解がないが、何をするサーバーかが伝わらない

Hub には、Docker Hub のようにベンダーが運営する共有のサービスに見えるおそれがある。説明文にセルフホストのサーバーであると書く。

### コアを private にしてレンダラーにバンドルする

コアのドメインロジック（JSON Schema と生成した型、パース、レイアウト、観測データの統合、シーンの組み立て、レイアウトの入力になるテーマの数値）は `libs/core` に置き、npm には公開しない。Hub のサーバーはレイアウトの計算（design.md §1.3）でコアだけを使う。

`libs/shumoku` の 1 パッケージにまとめず、コアとレンダラーを分ける理由:

- コアの `package.json` に Svelte を書かなければ、コアから Svelte を読み込めない。tsconfig の `lib` から DOM を外すことと、関数型スタイルの lint（「構成 A: すべて TypeScript」）も、パッケージの単位で掛けられる
- レンダラーだけを変えたときに、コアのビルドとテスト、Hub のサーバーのテストを省ける

コアを公開しない理由:

- shumoku は、部品を組み合わせるライブラリとしてではなく、製品として使ってもらう。外部に約束するのは、ファイル形式（JSON Schema）、レンダラーのコンポーネントの props、CLI のコマンドだけにする
- コアを公開すると、レイアウトの関数やシーンの型が semver の対象になる。レイアウトエンジンの境界（「レイアウトエンジンの境界」）は決まっていない

コアを公開しないので、次の作業が要る。

- `@shumoku/renderer` は、コアを依存に書けないので、ビルドでコアをバンドルする。`.d.ts` もコアの型を取り込んでまとめる（tsdown や api-extractor でできるが、試していない）
- `@shumoku/renderer` は、形式の型（`NetworkGraph` など）をエクスポートする。利用者がグラフのオブジェクトをコンポーネントに渡すためである。レイアウトの関数と中間の型はエクスポートしない
- CLI のビルドでは、コアを取り込み済みの `@shumoku/renderer` のビルド結果ではなく、レンダラーのソースをバンドルする。ビルド結果とコアを両方バンドルすると、CLI にコアが 2 つ入る

Svelte を使わずにレイアウトだけを使う利用者（YAML の検証だけをしたい、別のレンダラーを書きたい）は対象にしない。YAML の検証は CLI のコマンドで提供できる。

テキストの計測をフォントのデータから行う（「テキストの幅の計測」）なら、計測とフォントのファイルはコアに入り、Hub のサーバーにもフォントが入る。

### レンダラーをフレームワークごとに分けない

レンダラーは `@shumoku/renderer` の 1 パッケージにし、フレームワークごとの入り口はパスで分ける。リライト元は `@shumoku/renderer`、`@shumoku/renderer-svg`、`@shumoku/renderer-html`、`@shumoku/renderer-png` に分けていた。

- 利用者のバンドルに入るのは、読み込んだパスのコードだけである
- React、Vue、Svelte は optional な peer の依存にする
- リリースする版の組み合わせを、利用者が考えなくて済む

エクスポートは次の形を考えている。

| パス | 中身 | Svelte のランタイム |
|---|---|---|
| `@shumoku/renderer` | 形式の型 | なし |
| `@shumoku/renderer/svelte` | シーンを描くコンポーネント | peer |
| `@shumoku/renderer/element` | 自分で書いた custom element | バンドルする |
| `@shumoku/renderer/react`、`/vue` | 各フレームワークのラッパー | バンドルする |
| `@shumoku/renderer/ssr` | SVG の文字列を返す関数 | バンドルする |
| `@shumoku/renderer/schema.json` | `NetworkGraph` の JSON Schema | なし |

- グラフを受け取ってレイアウトから描く入り口と、計算済みのシーンを受け取って描く入り口を分ける。Hub の SPA はサーバーが計算したレイアウトを描くだけなので（design.md §1.3）、同じ入り口にすると SPA にレイアウトエンジンが入る
- custom element の登録（`customElements.define`）は副作用である。`sideEffects` に指定するか、登録する関数を利用者に呼んでもらう
- Hub と Drafter の SPA も、外部の利用者と同じエクスポートを使う

1 つのパッケージなので、React のラッパーだけの破壊的変更でも、パッケージ全体のメジャーが上がる。これは受け入れる。

#### ラッパーは Declarative Shadow DOM を出力する custom element を包む

React と Vue のラッパーは custom element を包む。custom element は Svelte の `customElement` オプションでは作らず、`HTMLElement` を継承するクラスを自分で書く。

- サーバーでは、ラッパーが `svelte/server` の `render()` で Svelte のコンポーネントを文字列にし、`<template shadowrootmode="open">`（Declarative Shadow DOM）に入れて custom element のタグの中に出力する。ブラウザは JS を待たずに図を描く
- クライアントでは、custom element が、shadow root に中身があれば Svelte の `hydrate()` を、なければ `mount()` を呼ぶ
- Svelte のランタイムとコンポーネントは shadow root の中で動き、React や Vue のランタイムと DOM を共有しない
- 色などの上書きは CSS 変数で行う（design.md §1.2）。CSS 変数は shadow root の中にも継承される

この形は試作していない。実装の前に次を確かめる。

1. shadow root を消さずに取得できるか。Declarative Shadow DOM で作られた shadow root を持つ要素に `attachShadow()` を呼ぶと、ブラウザは shadow root の中身を空にして返す（HTML の仕様の記述による。試していない）。コンストラクタでは `this.shadowRoot ?? this.attachShadow({ mode: 'open' })` のように、すでにある shadow root を使う
2. ハイドレーションに使う props をクライアントにどう渡すか。`hydrate()` には、サーバーで描いたときと同じ props（グラフかシーン）が要る。React の Server Component から custom element にオブジェクトのプロパティは渡らないので、JSON にして HTML に埋め込むか、ラッパーを Client Component にする。JSON を埋め込むと、図の SVG とデータの両方が HTML に入る
3. スタイルが shadow root に入るか。`render()` は `<style>` を `head` として返す。`<template>` の中に `<style>` を入れ、その状態で `hydrate()` が失敗しないか。クライアントで `mount()` したときに、Svelte が `<style>` を shadow root に入れるか
4. クライアントでの画面遷移で図が出るか。Declarative Shadow DOM は HTML のパーサーだけが処理する。React がクライアントで `<template shadowrootmode>` を DOM に足しても shadow root にならない。custom element が `<template>` の子を見つけたら、自分で shadow root に移す必要がある
5. React のハイドレーションで不一致の警告が出ないか。パーサーが `<template>` を shadow root に変えるので、React が期待する DOM に `<template>` がない。ラッパーが Server Component ならハイドレーションの対象にならないが、Client Component や Pages Router では対象になる
6. Next.js と Vite で、利用者がバンドラーの設定を変えずに使えるか。custom element を定義するモジュールを `'use client'` のファイルから読み込み、クライアントのバンドルに入れる

`@shumoku/renderer/ssr` の SVG の文字列を返す関数と CLI は、custom element を使わず、`render()` の結果をそのまま使う。Hub と Drafter の SPA は Svelte のコンポーネントを直接使う。

#### 却下: Svelte の customElement オプションで custom element を作る

Svelte のコンパイラの `customElement` オプションで custom element を作る案。クラスを自分で書かなくて済む。この方法で作った custom element は SSR では中身を出力しないので（Svelte 5 のドキュメントの記述による。試していない）、Next.js や Nuxt の SSR で図が出ず、design.md §1.1 の「組み込む利用者がビルド時や SSR で図を描ける」が Svelte の利用者にしか成り立たなくなるので却下した。

#### 却下: ラッパーが Svelte のコンポーネントを直接包む

ラッパーが、サーバーでは `svelte/server` で描いた SVG の文字列を埋め込み、クライアントでは Svelte のコンポーネントを React や Vue の DOM の中にマウントする案。custom element もラッパーの 1 つになる。Svelte と React が同じ DOM をハイドレーションしようとして衝突するので却下した。custom element と shadow root を挟めば、境界で分けられる。

### CLI をレンダラーと分ける

CLI は `@shumoku/cli` として、レンダラーとは別のパッケージで公開する。リライト元も同じ名前で公開している。

- CLI は PNG を出力する（design.md §1.1）。リライト元の CLI が PNG への変換に使う `@resvg/resvg-js` はネイティブのバイナリである。レンダラーに CLI を同梱すると、ページに図を埋め込むだけの利用者にもネイティブのバイナリが入る
- レンダラーのパッケージが、`bin`、ファイルの読み書き、引数の解析といった Node.js 専用のコードを持たない
- CLI のオプションを変えても、レンダラーのメジャーが上がらない

`@shumoku/renderer` と `@shumoku/cli` は、同じ版番号で一緒にリリースする。CLI がどの版のレンダラーで描くかを利用者が考えなくて済む。CLI だけの変更が頻繁になったら、版を分ける。

mermaid も、本体と `@mermaid-js/mermaid-cli` を分けている。

### カタログを private なパッケージにする

機器のカタログ（リライト元の `@shumoku/catalog`）は `libs/catalog` に置き、npm には公開しない。Hub と Drafter はアプリなので、ビルドでカタログを取り込む。

リライト元でカタログを使っているのは次の箇所である。

- editor: 製品の一覧、PoE の計算、カタログのポートの展開
- server: `discovery/deep-read.ts` の 1 か所。SNMP で読んだ `sysObjectID` から機種とベンダーを引く

カタログはコアにもレンダラーにも入れない。カタログは図の形式の一部ではなく、機種を足すたびにレンダラーの版が上がるのを避ける。

SNMP の読み取りをプラグインに移しても（「同時実行数の制限とキャンセルはプラグインのホストに閉じる」）、カタログのパッケージは要る。

- Drafter はカタログを使い続ける
- `sysObjectID` から機種を引く処理は、SNMP のプラグインに移っても残る。プラグインは QuickJS の中で動き（design.md §2.2）、ワークスペースのパッケージを実行時に読み込めない。カタログのデータをプラグインのビルドで取り込むか、ホストの関数として渡すかは決めていない

外部からカタログを使いたいという要望が出たら、公開に切り替える。

### Hub のパッケージの中の分け方

`apps/hub` は 1 つのパッケージにし、中をディレクトリで分ける案を考えている。

- API サーバーと SPA を `src/api` と `src/web` に分け、tsconfig と lint で境界を守る。リライト元は `apps/server/api` と `apps/server/web` の 2 つのパッケージに分けていた。SPA の依存は Vite がバンドルするので、すべて devDependencies に置ける
- 組み込みのプラグインは `apps/hub/plugins/` のディレクトリに置く。QuickJS で動かすスクリプトで（design.md §2.3）、使うのは Hub だけである。リライト元は `libs/plugins/*` に 9 つのパッケージを置いていた

Hub と Drafter で UI の部品（ボタンやダイアログ）を共有したくなったら、`libs/ui` のような private なパッケージに切り出す。最初は作らない。

### パッケージの分割と CI

リライト元は 9 つのパッケージ（`@shumoku/*` が 7 つ、`shumoku`、`@shumoku/cli`）を npm に公開している。公開するパッケージを 2 つにすると、次が減る。

- 依存の順にビルドするパッケージの数
- 版の決定、changelog、publish の回数。`@shumoku/renderer` と `@shumoku/cli` は同じ版番号でリリースするので、版の組み合わせも生じない

ワークスペースのパッケージが 7 つなら、Turborepo などのタスクランナーを使わず、GitHub Actions のパスの絞り込みとジョブの依存だけで足りる見込みである。

パッケージを減らすと、キャッシュと絞り込みの単位が粗くなる。パッケージの中のどこを変えても、そのパッケージ全体のビルドとテストが走る。コアとレンダラーを分けたので、最も重いと見込むレイアウトのテストは、コアを変えたときだけ走る。レンダラーの中（Svelte、React、Vue のラッパー）は、CI の時間が問題になるまで分けずに毎回すべて走らせる。

### リライト元が公開しているパッケージの扱い

リライト元が npm に公開しているパッケージのうち、v1.0.0 で名前を引き継ぐのは `@shumoku/renderer` と `@shumoku/cli` である。残りは非推奨にする。

- `@shumoku/core` と `@shumoku/catalog` は private にするので、非推奨にする。外部で直接使っている利用者がいるかを、リライト元の作者に確かめる
- `@shumoku/renderer-svg`、`@shumoku/renderer-html`、`@shumoku/renderer-png` は、`@shumoku/renderer` と `@shumoku/cli` に誘導する
- スコープなしの `shumoku` は、非推奨にして `@shumoku/renderer` に誘導する案に傾いている。`@shumoku/renderer` を再エクスポートするだけのパッケージとして残す案もある。名前から推測して `npm i shumoku` する人が古い版を入れずに済むが、公開するパッケージが 1 つ増え、`/react` などのエクスポートと peer の依存を二重に書くことになる。名前はリライト元が持っているので、要望が出てから 1.x として出せる

npm の名前を引き継ぐには、リライト元の作者の合意が要る。

### パッケージの分割で決まっていないこと

- Declarative Shadow DOM を出力する custom element が、SSR とハイドレーションで期待どおりに動くか（「ラッパーは Declarative Shadow DOM を出力する custom element を包む」）
- プラグインのホストの API の `.d.ts`（design.md §2.1）をどこで配るか。プラグインは Hub でしか動かないので、`@shumoku/renderer` には入れない。型だけのパッケージを公開する案と、Hub からダウンロードさせる案がある
- ファイル形式の版をファイルに書くか。Hub が保存したファイルを古い CLI が読む場合に要る。拡張子（`.shumoku.yaml` など）も決めていない
- Hub の版を `@shumoku/renderer` と別に付けるか。レンダラーの版はライブラリの利用者に、Hub の版は運用者に向けたものである
- スコープなしの `shumoku` の扱い（「リライト元が公開しているパッケージの扱い」）

### パッケージの分割で採らない案

- レンダラーと CLI を 1 つのパッケージ `shumoku` にまとめる案。`npx shumoku` で動き、リリースが 1 つで済む。PNG の変換に使うネイティブのバイナリを optional な peer の依存にするしかなく、PNG を出すには利用者が追加でインストールする必要がある（「CLI をレンダラーと分ける」）
- コアとレンダラーを 1 つのパッケージにまとめ、境界をディレクトリごとの tsconfig と lint で守る案。コアをバンドルする作業が要らない。境界をパッケージで守る方が確実で、CI の絞り込みも効く（「コアを private にしてレンダラーにバンドルする」）
- コアを `@shumoku/core` として公開し、レンダラーの通常の依存にする案。`.d.ts` をまとめる作業が要らない。コアの API が semver の対象になる（「コアを private にしてレンダラーにバンドルする」）
- レンダラーをスコープなしの `shumoku` として公開する案。名前から中身がわからず、`@shumoku/cli` と名前がそろわない
- レンダラーをフレームワークごとのパッケージに分ける案。読み込んだパスのコードだけがバンドルに入るので、分けても利用者のバンドルは小さくならない（「レンダラーをフレームワークごとに分けない」）
- カタログを `apps/drafter` の中に置く案。Hub がカタログを使い続ける場合に切り出すことになる（「カタログを private なパッケージにする」）

## ライセンス

パッケージごとのライセンスを決める。リライト元もこのリポジトリも、全体が AGPL-3.0 である。次の案に傾いている。ライセンスはリライト元の作者と決めるので、この節は作者に勧める案である。法律の専門家の確認は受けていない。

| 対象 | ライセンス |
|---|---|
| コア、レンダラー、CLI | Apache-2.0 |
| Hub、Drafter | AGPL-3.0 |
| プラグインのホストの API の型定義 | 緩いライセンスにし、プラグインは AGPL-3.0 の対象外と明記する |
| カタログ | 未決 |

ライセンスの境界はパッケージの境界に置く。Apache-2.0 のパッケージは AGPL-3.0 のパッケージに依存できない。「パッケージの分割」の依存の向きは、これを満たしている。

### レンダラーを AGPL-3.0 のままにできない理由

レンダラーの JS を自分のサイトのバンドルに入れてブラウザに送ると、ソフトウェアを配ることに当たる。AGPL-3.0 では、組み合わせて配るコードの全体を AGPL-3.0 と両立するライセンスで公開する義務が生じうる。ブログやドキュメントのサイトに図を埋め込むだけの利用者にこの義務が及ぶと、mermaid のように組み込んでもらう使い方（design.md §1.1）が成り立たない。

組み込んで使う図のレンダラーは、緩いライセンスで配られている。mermaid と Excalidraw は MIT、D2 は MPL-2.0 である（GitHub の表示で確かめた）。

### コア、レンダラー、CLI を Apache-2.0 にする

コア、レンダラー、CLI は Apache-2.0 にする。3 つは同じライセンスにそろえる。

- レンダラーと CLI はコアをバンドルして配る（「コアを private にしてレンダラーにバンドルする」）。コアだけを Apache-2.0 にしても、レンダラーが AGPL-3.0 のままなら、組み込む側への義務は残る
- CLI が出力する SVG にはレンダラーの CSS が入る。出力したファイルの扱いに疑問を残さないように、CLI もレンダラーと同じライセンスにする

MIT ではなく Apache-2.0 にする理由:

- 商標を許諾しないことが条文に書かれている。リライト元は `TRADEMARK.md` で名前とロゴの使い方を定めている
- 特許の許諾の範囲が条文に書かれている。コードを提供した人は、そのコードを使うと必ず侵害することになる特許だけを利用者に許諾し、特許権は持ち続ける。そのソフトウェアについて特許訴訟を起こした利用者は、特許の許諾を失う。MIT は特許に触れておらず、許諾の範囲が曖昧である
- ネットワークの分野に先例が多い。NetBox、Batfish、NAPALM、Nornir、OpenConfig は Apache-2.0 である（GitHub の表示で確かめた）
- AGPL-3.0 と GPL-3.0 にも同じ趣旨の特許の条項があるので、AGPL-3.0 から Apache-2.0 に変えても特許の許諾は失わない

今の権利者が特許を持っていなければ、特許の条項が実際に働く場面はほとんどない。効果は、利用する企業の審査に通りやすいことと、将来に企業がコードを提供したときの備えである。

Apache-2.0 のコードは AGPL-3.0 のソフトウェアに取り込めるので、Hub と Drafter はコアとレンダラーを使える。

Apache-2.0 のコードは、GPL-2.0 だけで配られているソフトウェアには組み込めない。GPL-2.0 は条文にない制限を足すことを禁じており、Apache-2.0 の特許の許諾の打ち切りがその制限に当たるとされている（FSF の解釈による）。「GPL-2.0 またはそれ以降」で配られているソフトウェアには組み込める。GPL-2.0 だけの古いソフトウェアにレンダラーが組み込まれることは想定しないので、この非互換は受け入れる。

### Hub と Drafter を AGPL-3.0 のままにする

Hub と Drafter は AGPL-3.0 のままにする。

- Hub は独立したサーバーであり、ほかのソフトウェアに組み込むライブラリではない。改変せずにデプロイして使うだけなら、利用者に生じる義務は実質的にない
- 改変した Hub をネットワーク越しに使わせる場合に、その利用者へソースコードを提供する義務が生じる。Hub のコードを非公開の製品に取り込むこともできない。AGPL-3.0 を残す目的はこの 2 つである
- Hub のデータソースである Zabbix と Grafana も AGPL-3.0 である（GitHub の表示で確かめた）。それらを運用している組織にとって、Hub のライセンスは導入の障害になりにくいと見ている（確かめていない）

AGPL-3.0 より厳しいライセンスにはしない。リライト元の商用サポート（`COMMERCIAL_SUPPORT.md`）は、ライセンスではなく、導入支援、データソースの連携、カスタムプラグインの開発などの作業を有償で提供している。ライセンスの販売やホスティングで収益を得ていないので、他社の利用を制限する理由がない。

### プラグインを AGPL-3.0 の対象外にする

プラグインのホストの API の型定義（design.md §2.1）は緩いライセンスで配り、利用者が書くプラグインは AGPL-3.0 の対象外であると明記する案を考えている。

- プラグインは Hub の中で動くので、何も書かなければ、Hub の派生物として AGPL-3.0 の対象になるかどうかが曖昧になる
- リライト元の `COMMERCIAL_SUPPORT.md` は、顧客向けに開発したプラグインを非公開のままにできるとしている。この扱いは、プラグインが AGPL-3.0 の対象外であることを前提にしている

明記する文面と、型定義をどのパッケージで配るか（「パッケージの分割で決まっていないこと」）は決めていない。組み込みのプラグインは Hub の一部として AGPL-3.0 にする。

### カタログのライセンス

カタログ（「カタログを private なパッケージにする」）のライセンスは決めていない。

- 使うのは Hub と Drafter だけなので、AGPL-3.0 でも困らない
- 中身は機器の仕様のデータである。コアと同じ Apache-2.0 にそろえておけば、あとで公開するときにライセンスを変えなくて済む
- SNMP のプラグインがカタログのデータを取り込む場合、そのプラグインを AGPL-3.0 の対象外にするなら、カタログも緩いライセンスである必要がある

### ライセンスを変えるのに要る同意

リライト元は、貢献者から著作権を譲り受ける CLA ではなく、DCO を使っている。既存のコードのライセンスを変えるには、そのコードを書いた人全員の同意が要る。

- 新しく書くコードの著作権は、取り決めがなければ書いた人にある。このリポジトリは外部の PR を受け付けていないので、権利者は増えない。このリポジトリで書く人と作者のあいだで、書いたコードをどのライセンスで提供するかを確かめておく
- リライト元のコードやテストを写して書き直した部分は、元のコードの派生物になりうる。コアとレンダラーでリライト元のコードを参照するなら、Apache-2.0 にすることへの同意を、その部分を書いた人から先に取る。リライト元の `libs/@shumoku/core` と `libs/@shumoku/renderer` にコミットがあるのは、bot を除いて 3 人である
- 同意が取れない部分は、リライト元のコードを見ずに書き直す

### ライセンスについて作者に確かめること

- コア、レンダラー、CLI を Apache-2.0 にしてよいか
- プラグインを AGPL-3.0 の対象外と明記してよいか（「プラグインを AGPL-3.0 の対象外にする」）
- カタログのライセンス（「カタログのライセンス」）
- リライト元のコアとレンダラーの貢献者から同意を取れるか（「ライセンスを変えるのに要る同意」）

### ライセンスで採らない案

コア、レンダラー、CLI について:

- MIT にする案。GPL-2.0 だけのソフトウェアにも組み込める。商標と特許の扱いが条文に書かれていない（「コア、レンダラー、CLI を Apache-2.0 にする」）
- MIT と Apache-2.0 のどちらかを利用者が選ぶ二重ライセンスにする案。GPL-2.0 だけのソフトウェアにも組み込める。MIT を選んだ利用者には、特許の許諾の打ち切りが効かない
- MPL-2.0 にする案。組み込む側のコードには義務が及ばず、shumoku のファイルを改変した場合だけ、そのファイルの公開を求められる。D2 が先例である。広く組み込んでもらうことを優先し、改変の公開は求めない
- AGPL-3.0 に、組み込みを認める例外の条項を足す案。独自の文面になり、利用する企業のライセンスの検査では AGPL-3.0 として扱われる
- LGPL にする案。利用者がライブラリを差し替えられる形で配ることを求めており、バンドルした JS でこの条件を満たす方法がはっきりしない

Hub と Drafter について:

- FSL、BSL、Elastic License v2、SSPL など、競合する利用やホスティングを制限するライセンスにする案。どれも OSI のオープンソースの定義を満たさないので、オープンソースと名乗れなくなる。利用を制限したい相手もいない（「Hub と Drafter を AGPL-3.0 のままにする」）
- AGPL-3.0 に商用利用の禁止などの条件を足す案。AGPL-3.0 は追加の制限を禁じており、受け取った人はその制限を外せる
- AGPL-3.0 のまま、AGPL-3.0 を使えない企業に別の商用ライセンスを売る案。ソフトウェアはオープンソースのままにできる。Hub を改変せずにデプロイするだけの企業は買う理由がなく、買うのは Hub のコードを自社の製品に取り込む企業に限られるので、今は採らない

## テキストの幅の計測

レイアウトの計算に使うテキストの幅を、DOM に依存せずに測る方法を決める。CLI と Node.js のライブラリ（design.md §1.1）はどちらの構成でも作るので、ブラウザと Node.js で同じ方法で測り、同じレイアウトを出す。

リライト元の `libs/@shumoku/core/src/layout/engine/text-measurer.ts` は、ブラウザでは canvas の `measureText` で測り、Node.js の SSR と CLI では em を単位にした控えめな推定に切り替えている。同じトポロジーでも、環境によってレイアウトの結果が変わる。

### フォントのデータから測る案

フォントのファイルを同梱し、グリフの送り幅とカーニングから幅を計算する。

- 構成 A では harfbuzzjs、fontkit、opentype.js など、構成 B では rustybuzz や ttf-parser などで測れる
- 計測が純粋な計算になるので、コアの中で測れる。TypeScript 側で先に測ってサイズ付きのグラフを渡す手順（「レイアウトエンジンの境界」）が要らなくなる
- 測ったフォントと描くフォントを一致させる必要がある。同じフォントを Web フォントとして配り、Svelte のコンポーネントの CSS で指定する
- 日本語を含むフォントはファイルが大きい。サブセット化するか、対象にする文字の範囲を絞る
- 組み込む側が別のフォントを使いたい場合の扱いを決める

### テキストの幅の計測で確かめること

- 同じフォントでも、ブラウザが描いた幅と計算した幅がどれだけずれるか（ヒンティング、サブピクセルの配置）。ずれをノードの余白で吸収できるか
