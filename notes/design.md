## システム構成

Server を API サーバーと SPA に分ける構成は未決である（「API サーバーと SPA の構成」ref:a8126291）。この節と ref:a369fc50、ref:a50bc664 は、その構成を前提に書いている。

<!-- id: 121eb88e -->
### 描画するシーンと Svelte のコンポーネントの分担

コアがレイアウトの結果から描画するシーンを組み立て、Svelte のコンポーネントがシーンを描く。

- コアが組み立てるシーンは、要素の種類と幾何データ（形、座標、大きさ、パスのセグメント、ラベルの文字列と位置）と、意味を表す属性（ノードの種類、状態、役割など）からなる
- Svelte は、シーンの要素の種類ごとにコンポーネントを持ち、SVG の要素に写してイベントを付ける
- 色、線の太さと種類、塗り、不透明度、ホバーや選択のときの見た目は、各コンポーネントの `<style>` に書く。ダークモードやテーマの切り替えと、組み込む側からの上書きは CSS 変数で行う。Svelte のスコープ付きのセレクタは詳細度が高く、外側から上書きしにくいためである

フォントの大きさ、ノードの内側の余白、ラベルの行の高さは、テキストの計測とレイアウトの計算に入るので、CSS だけには置かない。CSS だけで変えると、表示とレイアウトがずれる。これらはテーマの数値としてレイアウトの入力に含め、CSS には幾何データに影響しない値だけを置く。

描画はどの環境でも Svelte のコンポーネントで行い、SVG の出力器を別に持たない。

- SPA: コンポーネントが DOM に描く
- Node.js のライブラリと CLI（ref:e1a8fddf）: Svelte の SSR でコンポーネントを SVG の文字列にする

mermaid のように組み込むライブラリには Svelte のランタイムが入る。

<!-- id: e97a7bf3 -->
#### レイアウトエンジンとレンダラーを Node.js でも動かす

レイアウトエンジンとレンダラーは、ライブラリとして Node.js でも動くようにする。mermaid のように組み込む利用者が、自分のドキュメントサイトでビルド時や SSR で図を描けるようにするためである。テキストの幅の計測は DOM に依存させず、ブラウザと Node.js で同じ方法で測る。測り方は未決（「テキストの幅の計測」ref:366c46ab）。

<!-- id: 91278e8b -->
### レイアウトをサーバーで計算してキャッシュする

レイアウトは API サーバーで計算し、結果をキャッシュする。SPA ではレイアウトを計算しない。サーバーの外で計算するのは、CLI と組み込み用のライブラリだけである。リライト元では大きなトポロジーのレイアウトに数分かかり、サーバーで事前に計算して保存していた。

レイアウトエンジンは、CLI と組み込み用のライブラリでも動かす（ref:121eb88e、ref:e1a8fddf）。

サーバーと CLI で同じレイアウトを出すため、テキストの幅は DOM に依存せずに測る（「テキストの幅の計測」ref:366c46ab）。

サーバーと CLI で JS エンジンが違えば（Bun の JavaScriptCore と Node.js の V8 など）、`Math.hypot` の結果が一致する保証はない。ECMAScript は `Math.hypot` の精度を実装に任せている。リライト元のレイアウトが使う浮動小数点の関数は `Math.hypot` と `Math.sqrt` だけである。`sqrt` は IEEE 754 で正しく丸めることが決まっているので、どの環境でも同じ値になる。

<!-- id: c116015b -->
### 観測データの統合をコアに置く

観測データの統合は、各データソースと人の手入力がそれぞれ出したトポロジーを、1 つの `NetworkGraph` に合成する処理である。リライト元では `libs/@shumoku/core/src/observation/resolve.ts` の `resolve()` が担い、`(NetworkGraph[]) → NetworkGraph` の純粋関数になっている。

観測データの統合はコアのドメインロジックに含め、サーバーと CLI の両方で動かす。

<!-- id: fc0e0ab9 -->
### アイコンの SVG を画像として埋め込む

データとして受け取ったアイコンの SVG は、インラインで描かず、`<image href="data:image/svg+xml,...">` で画像として埋め込む。プラグイン、YAML、カタログのどれから来たアイコンも信頼しない。画像として読み込まれた SVG では、スクリプトが動かず、外部のリソースも読み込まれないので、サニタイズが要らない。

- SPA、Node.js のライブラリ、CLI のどれでも、同じ方法で安全に描ける。CLI が出力した SVG をブラウザで直接開いても、アイコンの中のスクリプトは動かない
- API サーバーは、アイコンの SVG をサニタイズせずに保存して返す。サーバーにサニタイザーが要らない
- アイコンの色は SVG に書かれたままになる。画像の中の SVG は埋め込む側の CSS 変数と `color` を継承せず、`currentColor` も効かないので、テーマやダークモードに合わせて色を変えられない

リライト元では、ノードの `spec.icon` が SVG の文字列か URL を持つ。プラグインから受け取ったアイコンを、API サーバーが取り込むときに jsdom と DOMPurify でサニタイズし（`apps/server/api/src/services/sanitize-icon.ts`）、レンダラーもブラウザの DOMPurify でサニタイズしてからインラインで描いている（`libs/@shumoku/renderer/src/components/svg/SvgNode.svelte`）。

<!-- id: 82efb887 -->
#### 却下: サニタイズしてインラインで描く

アイコンの SVG を DOMPurify でサニタイズし、インラインで描く案。CSS 変数でアイコンの色をテーマに合わせられる。

Node.js のライブラリと CLI でも描くので、ブラウザの外でもサニタイズが要る。Node.js で DOMPurify を使うには jsdom が要り、組み込み用のライブラリに入れるには重いので却下した。

## 使用言語

<!-- id: 82095d9a -->
### すべて TypeScript で書く

レイアウトエンジン、API サーバー、SPA（「API サーバーと SPA の構成」ref:a8126291）をすべて TypeScript で書く。サーバーに Effect を使うかは未決で、コアができてから決める（「サーバーに Effect を使うか」ref:6652de5e）。

検討した構成を次の名前で呼ぶ。採用したのは構成 A である。

- 構成 A: すべて TypeScript で書く
  - 構成 A.1: サーバーに Effect を使う
  - 構成 A.2: サーバーに valof と Result 型のライブラリを使う
- 構成 B: サーバーとコアのドメインロジックを Rust で書く。CLI とライブラリ向けにはコアを WASM にする

レイアウトエンジンは、lint（`let`、引数の再代入、破壊的な配列メソッドの禁止）と型を 1 モジュールに集める構成で関数型スタイルを守る。TypeScript にも判別可能な union と `never` による網羅性チェックがある。パターンマッチやイミュータブルなデータを簡潔に書くには、ts-pattern や valof などのライブラリを入れるか、`switch` と `readonly` で書く。構成 A.1 でも、純粋な計算をするコアに Effect のランタイムは持ち込まない。

利点:

- 観測データの統合とレイアウトエンジンを、WASM を介さずにサーバー、CLI、ライブラリで共有できる
- WASM のプラグインを Node.js がそのまま実行できる

欠点:

- 関数型スタイルを言語ではなくライブラリで得るので、ADT やパターンマッチは Rust より冗長になる
- Rust よりメモリの消費が大きい

<!-- id: 99479299 -->
#### 言語選定の動機

リライト元は TypeScript で書かれており、命令的なコードに流れやすく、型定義が分散していた。リライトでは関数型スタイルに寄せる。

レンダラーをアプリに組み込んで mermaid のように使うため、レイアウトエンジンは JS か WASM にコンパイルできる言語で書く必要がある。

リライト元のサーバー（`apps/server/api/src`、テストを除いて約 23,000 行）の中身は、データソースのポーリング、同期ジョブとその計画、観測データの統合、メトリクス、認証、スケジューラーである。状態の遷移、失敗の扱い、並行処理、I/O が絡み、ADT、`Result`、網羅的なパターンマッチといった言語の表現力が役立つ。言語の表現力は、レイアウトエンジンよりサーバーで役立つ。

<!-- id: 75728a23 -->
#### リライト元のサーバーで言語の表現力が役立つ範囲

リライト元のサーバーのうち、ADT と網羅的なパターンマッチが最も役立つのは一部である。行数はテストを除いて数えた。

| 部分 | 行数 | 表現力の役立ち方 |
|---|---|---|
| ルートとスキーマ（`modules/`） | 約 5,000 | 入出力の境界のコードで、zod でも serde でもほぼ同じ |
| DB を直接触る 15 ファイル | 約 7,500 | 境界のコードとロジックが混ざっている |
| プラグインのホスト（`plugins/`） | 約 2,700 | 構成 B では wasmtime の制限を使える |
| スケジューラー、同期の計画とジョブ、メトリクスの合成など 9 ファイル | 約 2,800 | 最も役立つ |

リライト元のサーバーには、次の書き方の問題がある。

- サーバーには `try {` が 132 個あり、`switch (` は 2 個しかない
- `services/sync-job.ts` の `SyncJob` は、`state`、`cancelRequested`、`finishedAt?` を別々のフィールドで持ち、完了したのに `finishedAt` がない状態を表せる
- `services/sync-plan.ts` の `SyncJobStep.key` は、ステップの種類を `fetch:<id>` のような文字列で表す

どれも判別可能な union と網羅性チェックで直せる。構成 B との差は、その書き方を言語が強制するか、lint とレビューが強制するかにある。Rust はエコシステム全体が `Result` を返し、変数が既定でイミュータブルである。構成 A では、ライブラリが投げる例外を I/O の境界で包み、`let` や `throw` を lint で禁じる。どのモジュールで何を禁じるかを最初に決め、CI で強制する。

<!-- id: 927d3a34 -->
#### リポジトリ内の言語の数

リポジトリ内の言語は 2 つまでにする。サーバーとレイアウトエンジンを、TypeScript 以外の別々の言語で書くと、クライアントの TypeScript と合わせて 3 つになる。この理由で、Rust のサーバーと MoonBit のレイアウトエンジンの組み合わせや、Scala か Elixir のサーバー（「却下: サーバーを Scala や Elixir などで書く」ref:c7d2d327）を外した。

プラグインは JavaScript で書いて WASM で動かす（ref:70cea09f）ので、この数には含めない。

<!-- id: a2192dfb -->
#### 却下: サーバーとコアを Rust で書く（構成 B）

サーバーと、レイアウトエンジン、観測データの統合、描画するシーンの組み立てといったコアのドメインロジックを Rust で書く案。サーバーはコアのクレートをネイティブのライブラリとしてリンクするので、サーバーとコアの間には WASM も JSON も要らず、型を共有できる。CLI とライブラリ向けには同じクレートを WASM にする。TypeScript 側は、シーンを Svelte のコンポーネントで描き、イベントを付けることだけを受け持つ。

Rust の表現力が最も役立つ範囲（「リライト元のサーバーで言語の表現力が役立つ範囲」ref:75728a23）に比べて、構成 B の欠点がかかる範囲が広いので却下した。リライト元の作者とプラグインを書くネットワークエンジニアは TypeScript を書いてきた。構成 B では、サーバーとコアへの貢献に Rust が要る。

利点:

- サーバーのロジックで役立つ表現力（ADT、`Result`、網羅的なパターンマッチ）が言語に組み込まれている
- wasmtime をプラグインのホストにでき、プラグインの実行時間とメモリを QuickJS とは別に WASM の層で制限できる
- 単一のバイナリで配れ、メモリの消費が小さい

欠点:

- CLI とライブラリ向けに、コアとの間に WASM の境界ができる
- DB のアクセスが構成 A より書きにくい
- 非同期 Rust が複雑
- コンパイルに時間がかかる
- 学習コストが TypeScript より高い

利点のうち次の 2 つは、構成 A との差が小さい。

- 単一のバイナリは、構成 A でも `bun build --compile` や Node.js の SEA で作れる。差はバイナリのサイズとメモリの消費で、小さな VM や Raspberry Pi で動かす利用者をどれだけ重く見るかで評価が変わる
- プラグインの実行時間は、構成 A でも VM を Worker で動かせば同じ深さで守れる。差はメモリの上限の掛けやすさと、Worker を立てるコストである

欠点のうち学習コストは最初に払えば済むが、WASM の境界、ネイティブと WASM の結果の一致、2 つのツールチェーン、sqlx のキャッシュ、コンパイル時間は保守のあいだ続く。コンパイル時間は、結果を見ながら何度も調整するレイアウトのヒューリスティックの作業で、影響が最も大きい。

構成 B では、wasmtime をプラグインの WASM のホストにする。epoch interruption か fuel で実行時間を、`ResourceLimiter` でメモリを、QuickJS とは別に WASM の層で制限できる。

リライト元は、QuickJS をサーバーのメインスレッドで動かし、実行時間の上限を QuickJS の `interruptHandler` だけで守っている（`apps/server/api/src/plugins/sandbox/quickjs-vm.ts`）。QuickJS のバグで割り込みの確認が実行されないと、サーバーのイベントループごと止まる。構成 A で実行時間について同じ深さの防御を得るには、VM を Worker で動かし、時間切れで `terminate()` する。

wasmtime の Component Model でホストとのインターフェースを型付きで定義できる点は、ほとんど差にならない。プラグインは JavaScript で書き、ホストと QuickJS の間のインターフェースは内部のもの（ref:68116cdd）なので、型付きの定義が役立つのは内部の実装だけである。

DB のアクセスは構成 A の方が書きやすい。構成 A では、Kysely を使えば条件を組み立てるクエリにも型が付く。構成 B で使う sqlx には次の問題がある（sqlx 0.9 系と Kysely 0.29 系の時点で確かめた）。

- sqlx の `query!` が検査するのは、文字列リテラルで書いた固定の SQL だけである。一覧の絞り込みのように条件を組み立てるクエリは `QueryBuilder` で書くが、SQL も結果の型も検査されない。Diesel なら組み立てるクエリにも型が付くが、ジェネリクスが重く、コンパイル時間とエラーメッセージが sqlx より悪くなる
- `query!` はコンパイル時に DB に接続するか、`cargo sqlx prepare` で作ったキャッシュを使う。キャッシュを CI で最新に保つ手間が加わり、マクロの分だけコンパイルも遅くなる
- Rust は型を名前で区別するので、行の構造体からドメインの型への詰め替えが要る。構成 A でも valof のブランド付きの型を使えば変換は要るが、Kysely ではテーブルの型の定義にブランド付きの型を直接書けるので、詰め替えを省ける

DB のアクセスは境界のコードなので、Rust の表現力（ADT、網羅的なパターンマッチ）がほとんど役立たない。リライト元のサーバーでは、DB を直接触るファイルがテストを除いて 15 個ある（`getDatabase()` か `.prepare(` を呼ぶもの）。

<!-- id: 4eff1c8e -->
#### 却下: レイアウトエンジンのコアだけを MoonBit で書く

構成 A のうち、レイアウトエンジンのコアだけを MoonBit で書き、JS バックエンドで出力する案（構成 C）。サーバーは TypeScript なので、Node.js が JS をそのまま実行する。

利点:

- ADT、パターンマッチ、イミュータブルな既定値がある。GC があるので、所有権モデルのためにグラフを扱うコードが書きにくくなることがない
- パターンマッチやイミュータブルなデータは言語の機能なので、ランタイムにライブラリが残らない
- JS バックエンドがあるので、WASM で問題になる非同期の初期化、バンドラーの設定、SSR や Edge ランタイムでの読み込みを避けられる
- レイアウトの計算は外部への依存が少ないので、エコシステムが薄くても困りにくい

利点が少ない割にリスクが大きいので却下した。

- 言語の表現力が役立つのはレイアウトエンジンだけである。表現力が最も役立つサーバー（「言語選定の動機」ref:99479299）は TypeScript のまま残る
- 言語がまだ 1.0 に達していない（0.8 系の時点で検討した）。ベータでコア言語は安定したと宣言されているが、標準ライブラリとツールチェーンは固まっていない
- グラフ、幾何、テストまわりのライブラリは自作になる可能性が高い
- 書ける人が少ない。コーディングエージェントも TypeScript ほど正確に書けない可能性がある
- TypeScript との境界の型が確かめられていない。MoonBit が公式に生成する `.d.ts` には `any` が混ざることがある。MoonBit の `struct` と `enum` が JS 上でどう表現されるか（`enum` の `$tag` など）は未確認で、TypeScript 側で値を直接組み立てられない可能性がある。mizchi/mbts（`.mbti` と `.d.ts` の相互変換）は開発が止まっている

1.0 が出ても、表現力が役立つ範囲がレイアウトエンジンに限られる点は変わらない。サーバーも MoonBit で書けるだけのサーバー向けのエコシステム（HTTP、DB、認証）が育ったら見直す。

<!-- id: 9a163a33 -->
#### 却下: レイアウトエンジンを TypeScript と Rust 以外の言語で書く

JS か WASM にコンパイルできる言語を候補にし、TypeScript と Rust 以外は次の理由で外した。MoonBit は「却下: レイアウトエンジンのコアだけを MoonBit で書く」ref:4eff1c8e で却下した。

- Elm は、JS から関数として呼べないので外した。JS とのやり取りは非同期の ports に限られ、同期の `layout(graph)` を提供できない。0.19.1 からリリースも止まっている
- PureScript はエコシステムと成熟度で外した
- Scala.js は、TypeScript との境界の型を扱いにくいので外した。Scala 3 で `.d.ts` を生成する道具がなく（sbt-scala-ts は Scala 2 系だけに対応する）、型を TypeScript 側で定義して ScalablyTyped で取り込むしかない。Scala 3 の高い表現力（型クラス、高カインド型など）も、純粋な計算のコアでは要らない
- Gleam は型の表現力が低く、制約を強めた TypeScript と大差ない。エコシステムもないので外した
- ReScript は、MoonBit と同じく表現力が役立つのがレイアウトエンジンだけなので外した（「却下: レイアウトエンジンのコアだけを MoonBit で書く」ref:4eff1c8e）。境界の型（`genType` による `.d.ts` の生成）と安定性が確かめられている点は MoonBit より有利だった
- OCaml（Melange / wasm_of_ocaml）は、ツールチェーン（dune、opam、Melange、JS のバンドラー）が重いので外した
- F#（Fable）は、.NET の標準ライブラリに依存したコードが JS に変換できないことがあり、Scala.js と同じく元のプラットフォームから引き継ぐ問題があるので外した
- Haskell は、GHC の JS バックエンドと WASM バックエンドが未成熟で、出力も重いので外した
- Kotlin/JS は、関数型が主体の言語ではなく、出力も重いので外した
- Roc、Koka、Grain は、研究段階かプレリリースで MoonBit より未成熟なので外した
- Go は WASM の出力サイズが大きいので外した

<!-- id: c7d2d327 -->
#### 却下: サーバーを Scala や Elixir などで書く

Scala と Elixir は、サーバーの言語としては悪くないが、リポジトリ内の言語が 3 つになるので外した（「リポジトリ内の言語の数」ref:927d3a34）。どちらもレイアウトエンジンを書けないため、レイアウトエンジンを書く言語が別に要る。

- Scala 3（JVM）: 型付きの副作用を扱うライブラリ（ZIO、Cats Effect）が最も成熟しており、型クラスや高カインド型といった表現力がサーバーのロジックで役立つ。WASM のプラグインは Chicory（Bytecode Alliance に移って Endive になった。QuickJS を動かす実績がある）で動かせる。長く動き続けるプロセスなので、JVM の起動時間やメモリの消費は大きな差にならない
- Elixir: BEAM はプロセスごとにヒープが分かれ、プリエンプティブにスケジュールされるので、プラグインだけでなくホスト自身のコードにバグがあっても、そのプロセスだけが落ちて全体は止まらない。スーパーバイザーが落ちたプロセスを再起動する。WASM は Wasmex（wasmtime を Rust の NIF として組み込んだライブラリ。Component Model に対応）で動かせる。ただし NIF の中でネイティブのコードがクラッシュすると BEAM 全体が落ちる。イミュータブルが基本なので、型が弱くても共有された状態に不整合が生じる種類のバグは起きにくい。型システムは、v1.20 で型推論による段階的な検査が入ったが、利用者が型を定義する手段はまだない（型付きの構造体は v1.21、型シグネチャは v1.22 で予定されている）

ほかに次の言語を外した。

- F#（.NET）は、構文のなじみやすさとエコシステムで Scala に劣るので外した。WASM のホストは公式の wasmtime-dotnet があり、Scala より素直である
- Kotlin（JVM）は、関数型が主体の言語ではないので外した。関数型に寄せるなら Scala を選ぶ
- Haskell は、ツールチェーンが重く、書ける人が少ないので外した
- OCaml は、ツールチェーンが重いので外した。wasmtime のバインディングも 0.0.3（wasmtime v0.22 に対応）で止まっており、WASM のホストとして弱い
- Gleam は、型の表現力が低いので外した。BEAM の並行処理はポーリングに向いている
- Go は、ADT がなく、関数型スタイルに寄せる動機に合わないので外した
- MoonBit（ネイティブ）は、サーバー向けのエコシステム（HTTP、DB、認証）がほとんどないので外した

プラグインが落ちても全体が止まらない隔離は、どの言語でも WASM のサンドボックスで得られる。wasmtime では、プラグインの trap はホストにエラー値として返り、メモリと実行時間に上限をかけられる。落ちた後の再起動は、Rust なら tokio のタスクの監視かアクターのライブラリ（ractor など）で書く。

<!-- id: a4fbf57d -->
### NetworkGraph を JSON Schema で定義する

トポロジーのモデル `NetworkGraph` は JSON Schema だけで定義し、各言語の型は JSON Schema から生成する。

- YAML を手書きするときに、エディタで補完が効く
- 他のアプリに組み込みやすい。Shumoku と違う言語で書かれたアプリでも、JSON Schema から型を生成できる

TypeScript の型は JSON Schema から生成する。生成した型の精度は試作で確かめる（「試作で確かめること」ref:1ce37d46）。

レイアウトエンジンの境界の型（「レイアウトエンジンの境界」ref:7dde35c3）は内部の型なので、JSON Schema で定義するかは決めていない。

## プラグイン

<!-- id: 2be7ede3 -->
### プラグインを JavaScript で書く

データソースのプラグインは JavaScript で書く。WASM にコンパイルしたプラグインは受け入れない。

プラグインの言語への要件:

- ネットワークエンジニアがコーディングエージェントに書かせて、すぐに試せる。コンパイルの手順を挟まないスクリプト言語で書ける
- サンドボックスで動かす。HTTP などの I/O は、ホストが許可リスト付きの関数として渡す

JavaScript を選んだ理由:

- QuickJS を WASM で動かす実績が多い。Shopify の Javy（Shopify Functions で本番運用されている）や Extism の JS PDK が QuickJS を使っている
- リライト元の `apps/server/api/src/plugins/sandbox/quickjs-vm.ts` の設計（VM の分離、メモリの上限、割り込みの期限、ポリシー付きの `fetch`）を引き継げる
- コーディングエージェントが正確に書ける。リライト元の 9 つのプラグインを移植の出発点にできる
- 素の JavaScript でも型の支援が得られる。Shumoku がホストの API の `.d.ts` を配れば、エディタ（TypeScript の言語サーバー）で補完が効き、JSDoc の型注釈と `// @ts-check` で型を検査できる

QuickJS は型を検査しない。TypeScript で書けるようにするなら、型を取り除く処理が要る。どこで行うかは ref:e30fdafe で確かめる。

| 観点 | JavaScript | Luau | Starlark |
|---|---|---|---|
| ネットワークエンジニアのなじみ | 中くらい | 低い | 高い（Python に近い） |
| コーディングエージェントの精度 | 高い | 中くらい | 中〜高（Python との違いで誤りやすい） |
| WASM で動かす実績 | 多い | 少ない | 確かめていない |
| コンパイルなしの型チェック | エディタでだけある（`.d.ts` と `@ts-check`） | ある | 一部ある |
| 非同期の I/O | Promise | コルーチン | ない（ホストに任せる） |
| リライト元のプラグイン | 移植しやすい | 書き直し | 書き直し |

<!-- id: 21a58987 -->
#### 却下: Luau

Roblox が開発している Lua の派生言語。段階的な型付けで、コンパイルの手順なしに型チェックが効く。最大の利点である言語に組み込まれたサンドボックスは、WASM の中で動かすとランタイムのサンドボックスと二重になり、利点が薄れる。WASM の中でホストから I/O を受け取るプラグインとして動かした事例がほとんど見当たらず、ネットワークエンジニアにもなじみが薄いので却下した。

<!-- id: 42e1f121 -->
#### 却下: Starlark

Python の方言で、Bazel のビルド設定などに使われている。ネットワークエンジニアになじみのある Python に構文が近い。I/O を持たない同期の言語で、クラスと例外がない。Rust 実装の `starlark-rust` はあるが、WASM の中で動かす事例は確かめていない。リライト元のプラグインは書き直しになる。

Python との違いで誤りやすく、組み込みのプラグイン（ref:c5fd4cca）を Starlark で書くとリポジトリの言語が 1 つ増えるので却下した。

<!-- id: ef63d381 -->
#### 却下: WASM にコンパイルしたプラグインも受け入れる

Rust、Go（TinyGo）、MoonBit などで書いて WASM にコンパイルしたプラグインも受け入れる案。わざわざ Rust や TinyGo でプラグインを書きたい利用者はいないと見込んで却下した。

Python に近い構文で WASM にコンパイルできる言語が出てきたら見直す。

<!-- id: 68116cdd -->
### プラグインを WASM のサンドボックスで動かす

Shumoku は QuickJS を WASM にビルドして同梱し、プラグインをその中で動かす。利用者はスクリプトを書くだけで、コンパイルは要らない。

- サンドボックスは WASM のランタイムに一本化する
- プラグインの作者に公開する API は JavaScript の関数だけである。ホストと QuickJS の間のインターフェースは内部のものなので、互換性を気にせず変えられる
- WASI のモジュールなので、Node.js がそのまま実行できる
- インタプリタを WASM の中で動かす分だけ遅くなるが、プラグインの処理はデータソースへの HTTP の待ち時間が中心なので問題になりにくい
- QuickJS は WASM の中で同期的に動くので、非同期の I/O はホストが作り込む。ホストの `fetch` が完了したらホストがゲストに入り直し、溜まった Promise のジョブを実行する。リライト元はこの形を実装済み

リライト元では、外部のプラグインを QuickJS の WASI ビルド（`quickjs-wasi`）で動かしている（`apps/server/api/src/plugins/sandbox/quickjs-vm.ts`）。データソースごとに VM を分け、メモリの上限、割り込みの期限、ネットワークのポリシー付きの `fetch` を実装している。

<!-- id: 8ddcc553 -->
#### 却下: QuickJS をネイティブで動かす

構成 B（ref:82095d9a）のサーバーで、QuickJS を WASM に入れずにネイティブのライブラリとして組み込み（Rust の `rquickjs` など）、その中でプラグインを動かす案。WASM の中で動かすより速い。QuickJS 自体も、メモリの上限、割り込み、ランタイムの分離を持ち、ホストが渡した関数以外の I/O を持たない。

QuickJS のバグがそのままサーバーへの侵入口になるので却下した。

- QuickJS は C で書かれており、メモリ安全性のバグが見つかり続けている。quickjs-ng では、型付き配列のヒープオーバーフローや Atomics の use-after-free などの CVE が続けて出ている
- ネイティブで動かすと、プラグインはエンジンのバグを突いて、DB とデータソースの認証情報を持つサーバーのプロセスで任意のコードを実行できる。プラグインがエンジンを落とすと、サーバー全体が止まる
- Shumoku はセルフホストなので、利用者はすぐには更新しない。エンジンの既知のバグが、動いているサーバーに長く残る
- WASM の中なら、エンジンのバグの被害は線形メモリの中に収まる。外に出られるのはホストが渡した関数だけで、エンジンが落ちても trap としてホストにエラー値が返る
- プラグインの処理はデータソースへの HTTP の待ち時間が中心なので、速度の差は問題になりにくい

V8（Rust の `rusty_v8`）をネイティブで動かす案も同じ理由で採らない。V8 は大規模なファジングと速い修正の体制を持つが、Chrome も Cloudflare Workers も、V8 だけには頼らずにプロセスの分離などの層を重ねている。

<!-- id: c5fd4cca -->
### 組み込みのプラグインも JavaScript で書く

組み込みのプラグインも JavaScript で書き、外部のプラグインと同じく QuickJS で動かす。利用者がプラグインを書くとき、組み込みのプラグインがサンプルになる。

リライト元では、Zabbix、NetBox、Prometheus、Grafana など 9 つの組み込みのプラグインを TypeScript で書き、サーバーと同じプロセスで動かしている（`apps/server/api/src/plugins/index.ts`）。QuickJS で動くのは外部のプラグインだけである。

QuickJS で性能が足りないプラグインが出たら、そのプラグインを TypeScript で書き直し、QuickJS の外で動かす。

<!-- id: 0b0deb90 -->
#### 却下: 遅い処理だけをホスト関数に移す

プラグインのうち遅い処理だけを、ホストが実装した関数として JavaScript に渡す案。ホスト関数は外部のプラグインからも呼べる公開の API になるので却下した。特定のプラグインの性能のために公開の API が増え、互換性を保つ対象も増える。

<!-- id: e30fdafe -->
### プラグインの実装で確かめること

実装の前に次を確かめる。

1. データソースのプラグインを 1 つ（たとえば Zabbix）コーディングエージェントに JavaScript で書かせ、書かれたコードがそのまま動くか
2. TypeScript で書けるようにする場合、型を取り除く処理をどこで行うか（ホストが読み込むとき、利用者の手元のツール、など）。素の JavaScript と `.d.ts` による型の支援で足りるなら、TypeScript には対応しない
3. 組み込みのプラグインの性能。大きな環境を想定したデータ（インターフェースが数千ある Zabbix、系列の多い Prometheus のクエリなど）で、処理時間とメモリを測る。性能の基準は、測った結果を見て決める。足りなければ、そのプラグインを QuickJS の外で動かす形に書き直す（ref:c5fd4cca）

## パッケージの分割

<!-- id: 1ef54310 -->
### ワークスペースの構成と依存の向き

LP 以外を 1 つのリポジトリに置き、ワークスペースを次のように分ける。npm には `@shumoku/renderer` と `@shumoku/cli` だけを公開する。LP は別のリポジトリにある。モノレポに戻すかは未決である（「LP をモノレポに戻すか」ref:c6570c50）。

```
libs/core/        private
libs/renderer/    公開（@shumoku/renderer）
libs/catalog/     private
apps/cli/         公開（@shumoku/cli）
apps/server/      private
apps/drafter/     private
apps/docs/        private
```

依存の向きを次のように制限する。

- `libs/core` は、ほかのワークスペースのパッケージに依存しない
- `libs/renderer` と `libs/catalog` は `libs/core` に依存する
- `apps/*` は `libs/*` に依存する。`libs/*` は `apps/*` に依存しない
- `libs/renderer` は `libs/catalog` に依存しない

<!-- id: a8224261 -->
#### LP 以外を 1 つのリポジトリに置く理由

LP 以外のパッケージは、互いの依存が強く、リポジトリを分けられない（リライト元の作者から聞いた）。

- モデルを複数のパッケージで共有する。YAML のスキーマを JSON Schema だけで定義し、TypeScript の型を生成する（ref:a4fbf57d）。スキーマを変えると、SPA、サーバー、CLI、ライブラリが一度に変わる。モノレポなら 1 つのコミットで変更してまとめてテストできる。リポジトリを分けると、スキーマのパッケージを公開してから各リポジトリで追従する手順になり、その間は版がずれる
- ドキュメントの例をワークスペースのレンダラーで描けば、例がそのままレンダラーのテストになる
- CI は最適化できる。変更されたパッケージとそれに依存するものだけをビルドしてテストする仕組みは Turborepo などにある。パスでの絞り込みやリモートキャッシュも使える

<!-- id: 2ee2a7b3 -->
#### 却下: パッケージの分け方の他の案

- レンダラーと CLI を 1 つのパッケージ `shumoku` にまとめる案。`npx shumoku` で動き、リリースが 1 つで済む。PNG の変換に使うネイティブのバイナリを optional な peer の依存にするしかなく、PNG を出すには利用者が追加でインストールする必要がある（ref:e1a8fddf）
- コアとレンダラーを 1 つのパッケージにまとめ、境界をディレクトリごとの tsconfig と lint で守る案。コアをバンドルする作業が要らない。境界をパッケージで守る方が確実で、CI の絞り込みも効く（ref:eb43d442）
- コアを `@shumoku/core` として公開し、レンダラーの通常の依存にする案。`.d.ts` をまとめる作業が要らない。コアの API が semver の対象になる（ref:eb43d442）
- レンダラーをスコープなしの `shumoku` として公開する案。名前から中身がわからず、`@shumoku/cli` と名前がそろわない
- レンダラーをフレームワークごとのパッケージに分ける案。読み込んだパスのコードだけがバンドルに入るので、分けても利用者のバンドルは小さくならない（ref:e83fe23c）
- カタログを `apps/drafter` の中に置く案。Server がカタログを使い続ける場合に切り出すことになる（ref:c8e16e31）

<!-- id: 35645edd -->
### 製品の名前

パッケージとディレクトリの名前は、次の製品の名前に合わせる。

- shumoku: ファイル形式と、そのレンダラーの名前。mermaid と同じ使い方である
- Shumoku Server: リライト元の server に当たる
- Shumoku Drafter: リライト元の editor に当たる

Server という名前は、暗黙に使われてきた呼び方を明示したものである。

- リライト元のリポジトリは `server` というディレクトリ名でほかと区別しており、開発者の間でも shumoku server と呼んでいた
- 利用者は、Shumoku を Shumoku Server のことだと受け取っている。Server を付け足すほうが、Hub を付け足すより驚かれにくい
- ネットワークの分野では、Server という名前はオンプレミスにデプロイできるという印象を与える（リライト元の作者から聞いた）

<!-- id: 97fbbdf7 -->
#### 却下: Shumoku Hub などの名前

Server のほかに、次の名前を検討した。

- Hub は、複数のデータソースから集める場所という意味になる。リライト元の作者によれば、Hub にはそこからどこかへ飛べるという含意があり、実態に合わない。Docker Hub のようにベンダーが運営する共有のサービスに見えるおそれもある
- Collector は、OpenTelemetry Collector のように、集めて転送するだけで画面を持たないエージェントに見える
- Nexus は Cisco のスイッチの製品名、Central は Aruba Central と重なる
- Atlas は、集まった図を見る場所という意味になり、データソースから集める意味が弱い

<!-- id: eb43d442 -->
### コアを private にしてレンダラーにバンドルする

コアのドメインロジック（JSON Schema と生成した型、パース、レイアウト、観測データの統合、シーンの組み立て、レイアウトの入力になるテーマの数値）は `libs/core` に置き、npm には公開しない。Server の API サーバーはレイアウトの計算（ref:91278e8b）でコアだけを使う。

`libs/shumoku` の 1 パッケージにまとめず、コアとレンダラーを分ける理由:

- コアの `package.json` に Svelte を書かなければ、コアから Svelte を読み込めない。tsconfig の `lib` から DOM を外すことと、関数型スタイルの lint（ref:82095d9a）も、パッケージの単位で掛けられる
- レンダラーだけを変えたときに、コアのビルドとテスト、Server の API サーバーのテストを省ける

コアを公開しない理由:

- shumoku は、部品を組み合わせるライブラリとしてではなく、製品として使ってもらう。外部に約束するのは、ファイル形式（JSON Schema）、レンダラーのコンポーネントの props、CLI のコマンドだけにする
- コアを公開すると、レイアウトの関数やシーンの型が semver の対象になる。レイアウトエンジンの境界は決まっていない（「レイアウトエンジンの境界」ref:7dde35c3）

コアを公開しないので、次の作業が要る。

- `@shumoku/renderer` は、コアを依存に書けないので、ビルドでコアをバンドルする。`.d.ts` もコアの型を取り込んでまとめる（tsdown や api-extractor でできるが、試していない）
- `@shumoku/renderer` は、形式の型（`NetworkGraph` など）をエクスポートする。利用者がグラフのオブジェクトをコンポーネントに渡すためである。レイアウトの関数と中間の型はエクスポートしない
- CLI のビルドでは、コアを取り込み済みの `@shumoku/renderer` のビルド結果ではなく、レンダラーのソースをバンドルする。ビルド結果とコアを両方バンドルすると、CLI にコアが 2 つ入る

Svelte を使わずにレイアウトだけを使う利用者（YAML の検証だけをしたい、別のレンダラーを書きたい）は対象にしない。YAML の検証は CLI のコマンドで提供できる。

テキストの計測をフォントのデータから行う（「テキストの幅の計測」ref:366c46ab）なら、計測とフォントのファイルはコアに入り、Server の API サーバーにもフォントが入る。

<!-- id: e83fe23c -->
### レンダラーをフレームワークごとに分けない

レンダラーは `@shumoku/renderer` の 1 パッケージにし、フレームワークごとの入り口はパスで分ける。リライト元は `@shumoku/renderer`、`@shumoku/renderer-svg`、`@shumoku/renderer-html`、`@shumoku/renderer-png` に分けていた。

- 利用者のバンドルに入るのは、読み込んだパスのコードだけである
- React、Vue、Svelte は optional な peer の依存にする
- リリースする版の組み合わせを、利用者が考えなくて済む

エクスポートは次の形を考えている。

| パス | 中身 | Svelte のランタイム |
|---|---|---|
| `@shumoku/renderer` | 形式の型 | なし |
| `@shumoku/renderer/svelte` | シーンを描くコンポーネント | peer |
| `@shumoku/renderer/element` | 自分で書いた custom element | バンドルする |
| `@shumoku/renderer/react`、`/vue` | 各フレームワークのラッパー | バンドルする |
| `@shumoku/renderer/ssr` | SVG の文字列を返す関数 | バンドルする |
| `@shumoku/renderer/schema.json` | `NetworkGraph` の JSON Schema | なし |

- グラフを受け取ってレイアウトから描く入り口と、計算済みのシーンを受け取って描く入り口を分ける。Server の SPA はサーバーが計算したレイアウトを描くだけなので（ref:91278e8b）、同じ入り口にすると SPA にレイアウトエンジンが入る
- custom element の登録（`customElements.define`）は副作用である。`sideEffects` に指定するか、登録する関数を利用者に呼んでもらう
- Server と Drafter の SPA も、外部の利用者と同じエクスポートを使う

1 つのパッケージなので、React のラッパーだけの破壊的変更でも、パッケージ全体のメジャーが上がる。これは受け入れる。

#### ラッパーは Declarative Shadow DOM を出力する custom element を包む

React と Vue のラッパーは custom element を包む。custom element は Svelte の `customElement` オプションでは作らず、`HTMLElement` を継承するクラスを自分で書く。

- サーバーでは、ラッパーが `svelte/server` の `render()` で Svelte のコンポーネントを文字列にし、`<template shadowrootmode="open">`（Declarative Shadow DOM）に入れて custom element のタグの中に出力する。ブラウザは JS を待たずに図を描く
- クライアントでは、custom element が、shadow root に中身があれば Svelte の `hydrate()` を、なければ `mount()` を呼ぶ
- Svelte のランタイムとコンポーネントは shadow root の中で動き、React や Vue のランタイムと DOM を共有しない
- 色などの上書きは CSS 変数で行う（ref:121eb88e）。CSS 変数は shadow root の中にも継承される

この形は試作していない。実装の前に次を確かめる。

1. shadow root を消さずに取得できるか。Declarative Shadow DOM で作られた shadow root を持つ要素に `attachShadow()` を呼ぶと、ブラウザは shadow root の中身を空にして返す（HTML の仕様の記述による。試していない）。コンストラクタでは `this.shadowRoot ?? this.attachShadow({ mode: 'open' })` のように、すでにある shadow root を使う
2. ハイドレーションに使う props をクライアントにどう渡すか。`hydrate()` には、サーバーで描いたときと同じ props（グラフかシーン）が要る。React の Server Component から custom element にオブジェクトのプロパティは渡らないので、JSON にして HTML に埋め込むか、ラッパーを Client Component にする。JSON を埋め込むと、図の SVG とデータの両方が HTML に入る
3. スタイルが shadow root に入るか。`render()` は `<style>` を `head` として返す。`<template>` の中に `<style>` を入れ、その状態で `hydrate()` が失敗しないか。クライアントで `mount()` したときに、Svelte が `<style>` を shadow root に入れるか
4. クライアントでの画面遷移で図が出るか。Declarative Shadow DOM は HTML のパーサーだけが処理する。React がクライアントで `<template shadowrootmode>` を DOM に足しても shadow root にならない。custom element が `<template>` の子を見つけたら、自分で shadow root に移す必要がある
5. React のハイドレーションで不一致の警告が出ないか。パーサーが `<template>` を shadow root に変えるので、React が期待する DOM に `<template>` がない。ラッパーが Server Component ならハイドレーションの対象にならないが、Client Component や Pages Router では対象になる
6. Next.js と Vite で、利用者がバンドラーの設定を変えずに使えるか。custom element を定義するモジュールを `'use client'` のファイルから読み込み、クライアントのバンドルに入れる

`@shumoku/renderer/ssr` の SVG の文字列を返す関数と CLI は、custom element を使わず、`render()` の結果をそのまま使う。Server と Drafter の SPA は Svelte のコンポーネントを直接使う。

#### 却下: Svelte の customElement オプションで custom element を作る

Svelte のコンパイラの `customElement` オプションで custom element を作る案。クラスを自分で書かなくて済む。この方法で作った custom element は SSR では中身を出力しないので（Svelte 5 のドキュメントの記述による。試していない）、Next.js や Nuxt の SSR で図が出ず、ref:e97a7bf3 の「組み込む利用者がビルド時や SSR で図を描ける」が Svelte の利用者にしか成り立たなくなるので却下した。

<!-- id: ca6ea394 -->
#### 却下: ラッパーが Svelte のコンポーネントを直接包む

ラッパーが、サーバーでは `svelte/server` で描いた SVG の文字列を埋め込み、クライアントでは Svelte のコンポーネントを React や Vue の DOM の中にマウントする案。custom element もラッパーの 1 つになる。Svelte と React が同じ DOM をハイドレーションしようとして衝突するので却下した。custom element と shadow root を挟めば、境界で分けられる。

### CLI をレンダラーと分ける

CLI は `@shumoku/cli` として、レンダラーとは別のパッケージで公開する。リライト元も同じ名前で公開している。

- CLI は PNG を出力する。リライト元の CLI が PNG への変換に使う `@resvg/resvg-js` はネイティブのバイナリである。レンダラーに CLI を同梱すると、ページに図を埋め込むだけの利用者にもネイティブのバイナリが入る
- レンダラーのパッケージが、`bin`、ファイルの読み書き、引数の解析といった Node.js 専用のコードを持たない
- CLI のオプションを変えても、レンダラーのメジャーが上がらない

`@shumoku/renderer` と `@shumoku/cli` は、同じ版番号で一緒にリリースする。CLI がどの版のレンダラーで描くかを利用者が考えなくて済む。CLI だけの変更が頻繁になったら、版を分ける。

mermaid も、本体と `@mermaid-js/mermaid-cli` を分けている。

### カタログを private なパッケージにする

機器のカタログ（リライト元の `@shumoku/catalog`）は `libs/catalog` に置き、npm には公開しない。Server と Drafter はアプリなので、ビルドでカタログを取り込む。

リライト元でカタログを使っているのは次の箇所である。

- editor: 製品の一覧、PoE の計算、カタログのポートの展開
- server: `discovery/deep-read.ts` の 1 か所。SNMP で読んだ `sysObjectID` から機種とベンダーを引く

カタログはコアにもレンダラーにも入れない。カタログは図の形式の一部ではなく、機種を足すたびにレンダラーの版が上がるのを避ける。

SNMP の読み取りをプラグインに移しても（「プラグインのホストの境界」ref:d1f44bdd）、カタログのパッケージは要る。

- Drafter はカタログを使い続ける
- `sysObjectID` から機種を引く処理は、SNMP のプラグインに移っても残る。プラグインは QuickJS の中で動き（ref:68116cdd）、ワークスペースのパッケージを実行時に読み込めない。カタログのデータをプラグインのビルドで取り込むか、ホストの関数として渡すかは決めていない

外部からカタログを使いたいという要望が出たら、公開に切り替える。

### パッケージの分割と CI

リライト元は 9 つのパッケージ（`@shumoku/*` が 7 つ、`shumoku`、`@shumoku/cli`）を npm に公開している。公開するパッケージを 2 つにすると、次が減る。

- 依存の順にビルドするパッケージの数
- 版の決定、changelog、publish の回数。`@shumoku/renderer` と `@shumoku/cli` は同じ版番号でリリースするので、版の組み合わせも生じない

ワークスペースのパッケージが 7 つなら、Turborepo などのタスクランナーを使わず、GitHub Actions のパスの絞り込みとジョブの依存だけで足りる見込みである。

パッケージを減らすと、キャッシュと絞り込みの単位が粗くなる。パッケージの中のどこを変えても、そのパッケージ全体のビルドとテストが走る。コアとレンダラーを分けたので、最も重いと見込むレイアウトのテストは、コアを変えたときだけ走る。レンダラーの中（Svelte、React、Vue のラッパー）は、CI の時間が問題になるまで分けずに毎回すべて走らせる。

<!-- id: 544af488 -->
### リライト元が公開しているパッケージの扱い

リライト元が npm に公開しているパッケージのうち、v1.0.0 で名前を引き継ぐのは `@shumoku/renderer` と `@shumoku/cli` である。残りは非推奨にする。

- `@shumoku/core` と `@shumoku/catalog` は private にするので、非推奨にする。外部で直接使っている利用者がいるかを、リライト元の作者に確かめる
- `@shumoku/renderer-svg`、`@shumoku/renderer-html`、`@shumoku/renderer-png` は、`@shumoku/renderer` と `@shumoku/cli` に誘導する
- スコープなしの `shumoku` の扱いは未決である（「パッケージの分割で決まっていないこと」ref:330f7fe0）

## 開発ツールと依存の更新

<!-- id: 2d1f414a -->
### ツールを mise で入れる

Node.js、pnpm、GitHub Actions のワークフローのリンター（actionlint、shellcheck、ghalint、zizmor、pinact）を mise で入れる。ツールチェーンの版を固定するためである。版は `mise.toml` に書き、`mise.lock` で固定する。CI も `jdx/mise-action` で同じ版を入れる。

- Node.js は、`mise.toml` でメジャーの番号を指定する（`"26"`）。`"lts"` にすると、次のメジャーが LTS になった週に `mise.lock` だけが変わり、承認を経ずに週 1 回の PR に入る。pnpm のカタログの `@types/node` のメジャーとも食い違う
- 公開から 3 日経っていない版は入れない（`minimum_release_age`）。理由は ref:326eca90 に書く
- `vp` は mise では入れられないので（[vite-plus#943](https://github.com/voidzero-dev/vite-plus/issues/943)）、pnpm で入れた vite-plus の `bin` を PATH に足す

<!-- id: 326eca90 -->
### 依存の更新に Renovate を使う

Renovate は、アクション、mise のツール、npm の依存を 1 つの設定で更新する。Dependabot の version updates は mise に対応していない。

通常の更新は、対象ごとに週 1 回の PR にまとめる。更新の PR を毎日出すと、その更新が緊急かどうかを人が PR ごとに判定することになる。緊急の更新は、更新の PR ではなく、脆弱性の検査で知る。npm の依存は Dependabot alerts で検査する（ref:038438e6）。ほかの対象の検査は未決である（「依存の脆弱性の検査」ref:26f089f1）。

Renovate を使うには、Mend の GitHub App にリポジトリへの書き込み権限を与える。GitHub App を入れられるのは組織のオーナーである。

Renovate の設定（`.github/renovate.json`）:

- 週 1 回の PR は、日本時間の月曜 0 時から 4 時の間に作る（`schedule:earlyMondays` と `timezone: Asia/Tokyo`）
- PR は人がマージする。オートマージは使わない。PR を放置しても、Renovate は対象ごとに同じ PR を作り直すので、PR は増えない
- npm の依存は、範囲の中の更新をロックファイルの保守の PR に任せ、範囲を書き換える更新だけを別の PR にする。推移的な依存を更新できるのは保守だけで、Renovate は保守を他の更新と同じ PR にまとめられない
- mise のツールは保守の対象にしない。通常の更新が `mise.lock` を書き換えるので、保守と中身が重なる
- メジャー更新は承認制にする（`:approveMajorUpdates`）。Renovate が Dependency Dashboard の issue に一覧し、人がチェックを入れたものだけを PR にする。メジャー更新は移行の作業を伴うので、着手する時期を人が決める
- 公開から 3 日経っていない版は入れない（`minimumReleaseAge`）。Renovate が npm のパッケージに勧める値で、npm が公開の取り消しを認める 72 時間を越える。pnpm と mise にも同じ値を設定してある（`pnpm-workspace.yaml`、`mise.toml`）
- 脆弱性の修正の PR は Renovate が作る。Dependabot は alerts だけを有効にし、security updates は有効にしない。両方を有効にすると、同じ修正の PR が 2 つ出る
- 脆弱性の修正の PR は待機期間を待たない。pnpm は脆弱性の修正を区別しないので、Renovate が修正版を `pnpm-workspace.yaml` の `minimumReleaseAgeExclude` に書き足す。修正版が連れてくる新しい推移的な依存は書き足されない。インストールが失敗したら手で足す
- コミットメッセージは Renovate の既定のまま、英語にする。bot のコミットは、日本語で書く規約の例外とする（`AGENTS.md`）

Renovate が pnpm のカタログ（`pnpm-workspace.yaml`）と `mise.lock` を更新できるかは、Mend がホストするアプリでは確かめていない。

<!-- id: 43386558 -->
#### 却下: Renovate を脆弱性の修正だけに絞る

`security:only-security-updates` で、Renovate を脆弱性の修正だけに絞る案。Renovate は、SHA で固定したアクションと mise のツールの脆弱性を知る経路を持たないので却下した。

<!-- id: 5b26ec14 -->
#### 却下: mise のツールの更新だけを毎日にする

mise のツールの更新だけを毎日の PR にする案。PR ごとに緊急かどうかを人が判定することになるので却下した。

<!-- id: 038438e6 -->
### npm の依存の脆弱性を Dependabot alerts で検査する

Dependabot は alerts だけを有効にする。脆弱性の修正の PR は Renovate が作る（ref:326eca90）。

Dependabot alerts は、アドバイザリの公開時に通知する。Dependabot は pnpm 12 に対応済みである（[dependabot-core#16095](https://github.com/dependabot/dependabot-core/issues/16095)）。

アクションの脆弱性には使えない。GitHub は、アクションの alerts を、セマンティックバージョンで指定したものにだけ出す。このリポジトリはアクションを SHA で固定している。
